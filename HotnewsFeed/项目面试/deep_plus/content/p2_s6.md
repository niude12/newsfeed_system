# 《项目之外 · Agent 通用技术面试深度解析》
## 六、Skills、Tools、MCP 与可复用能力（第 41-48 题）

### Q41. 你觉得 Agent Skills 是什么？
【深度回答】
先给结论：技能（Skill：打包成可复用单元的能力，含名称/描述/参数/使用说明与配套资源，本质是 Agent 的任务操作手册）不是单个功能按钮，而是一整套可重复执行的做事方法——它告诉 Agent 什么时候适用、要读什么资料、按什么步骤做、用哪些脚本、最后怎么验收。

分层展开看，一个 Skill 由三层构成：第一，元信息层。`name`、`description` 等字段让 Agent（智能体：能自主决策、调用工具并循环执行任务的人工智能系统）能在一堆技能里发现并匹配它，回答"这个技能管什么场景、何时不要用"。第二，操作层。正文用自然语言描述触发条件、前置条件、分步流程、输出验收标准、错误回退与安全边界，回答"具体怎么做"。第三，资源层。配套脚本、模板、参考文档、示例文件，按需加载而不是启动时就全读进来。把团队反复做的经验固化成 Skill 后，Agent 每次执行都不需要重新解释整套流程，新上下文也能复用同一套做法——这就是它的核心价值：把隐性经验显性化。

举例：一个"PDF 导出"Skill 不只是"会生成 PDF"的能力声明，它还规定字体与排版规范、渲染后必须截图检查、临时文件放哪里、最终交付哪种格式——把团队踩过的坑写进流程。

注意与边界：Skill 本质是"内容"而非"代码逻辑"，质量取决于是否写得可执行、可测试；它不同于工具（Tool：Agent 可调用的外部函数/API）——Tool 是原子动作，Skill 是编排这些动作的流程；Skill 应可版本化，并允许用户指令覆盖非安全性的默认值。
- 关键点：Skill 是"任务操作手册+配套资源"的可复用封装；含元信息、操作步骤、资源三层；价值在于沉淀团队经验、避免每次重新解释流程。

### Q42. Skill、Prompt、Tool、MCP Server、Plugin 有什么区别？
【深度回答】
先给结论：一句话区分——提示词（Prompt：本次对话交给模型的指令文本）是"这次怎么答"，工具（Tool：Agent 可调用的外部函数/API）是"执行动作"，MCP（Model Context Protocol，模型上下文协议：Agent 连接外部工具与数据源的标准通信协议）是"连接工具的标准化管道"，技能（Skill：可复用的任务操作手册与配套资源）是"一类任务怎么做"，插件（Plugin：把一组能力打包并便于安装分发的载体）是"怎么分发装包"。它们职责不同，但会组合使用。

分层展开：Prompt 只影响单次推理，告诉模型输出格式与约束；Tool 是一个能被模型通过工具调用（Tool Calling / Function Calling：模型根据工具 schema 输出调用意图的机制）触发的具体动作，如 `export_pdf(path)`；MCP 是一种协议，MCP 服务器（MCP Server：通过 MCP 协议暴露工具、资源和提示词的服务端）把工具以统一结构暴露给宿主（Host：运行 Agent 并连接 MCP 服务器的应用），解决"每个工具一套集成方式"的碎片化；Skill 是在工具之上的编排层，把多个工具调用、检查点、验收步骤串成一个流程；Plugin 则是分发单元，负责把上述能力打包、签名、安装、升级，类似软件的安装包。一句话总结各层位置：

```
Prompt：这次怎么答（本次指令）
Tool  ：执行动作（原子函数/API）
MCP   ：标准化连接（协议，暴露 Tool/Resource/Prompt）
Skill ：一类任务怎么做（流程+资源）
Plugin：分发安装（打包载体）
```

举例：Tool 是"执行导出 PDF"的按钮；Skill 是从读材料、排版、渲染检查到验收交付的整套操作手册；MCP 负责让 Agent 用同一套方式调用这个导出按钮；Plugin 负责把这一切分发到用户的 Agent 环境里。

注意与边界：它们可以互相包含——Skill 内部会调用 Tool，Plugin 里可能装着多个 Skill；区分的关键是问"它解决什么问题"：是本次指令、原子动作、连接协议、流程编排，还是安装分发。面试时用"职责不同、组合使用"收尾即可。
- 关键点：Prompt 指指令、Tool 指动作、MCP 指连接协议、Skill 指流程、Plugin 指分发载体；五者职责不同且常组合使用。

### Q43. 为什么 Skill 要采用渐进式披露？
【深度回答】
先给结论：渐进式披露（Progressive Disclosure：先暴露简短名称与描述，任务匹配后再按需加载全文与资源的机制）是为了在"让 Agent 找得到技能"和"不浪费上下文预算"之间取得平衡——如果启动时把所有 Skill 的全文和脚本都塞进窗口，token 预算（Token Budget：一次推理窗口可用的 token 配额）会被迅速耗尽，还会干扰模型对工具的准确选择。

分层展开：第一，上下文效率。一个大型 Agent 可能挂几十上百个长尾技能（Long-tail Skills：数量多、单次触发概率低、但对特定场景有价值的技能），全文全量加载会挤占真正需要的任务信息与工具 schema（Tool Schema：描述函数名、参数、返回值的结构定义）空间。第二，可发现性。渐进式披露仍要保证所有 Skill 的短名与描述在启动时可见，让模型"知道有哪些能力存在"，这是能力发现（Capability Discovery：让 Agent 找到可用能力的过程）的基础。第三，精度。描述足够具体时，模型先做粗匹配；确认命中后再读取完整 `SKILL.md`；只有执行到某一步才加载对应的模板、脚本或参考文件——真正需要的细节恰好到达，多余的资源不进上下文。

举例：会话开始时，模型只看到一列 Skill 名称与一句话描述；当任务确认是"生成 PDF"后，才把 PDF Skill 的完整 `SKILL.md` 读入；其中"渲染检查"步骤需要脚本时，才把该脚本加载进来。

注意与边界：渐进式披露依赖"描述写得好"，描述含糊会导致匹配失败或选错；同时要防止只披露名称而信息不足，让模型不知道该触发哪个。通常做法是描述里写清触发场景、输入与不做的事，并配合选择评测来迭代。
- 关键点：渐进式披露=先摘要后全文、按需加载资源；兼顾上下文效率、可发现性与专业细节；质量取决于 Skill 描述是否足够区分。

### Q44. 一个高质量 SKILL.md 应包含什么？
【深度回答】
先给结论：一份高质量的 `SKILL.md`（技能清单文件：用 Markdown（一种轻量级标记语言）描述技能元信息与操作步骤的标准文件）应当让一个从没见过该技能的 Agent 也能正确、安全、可验证地执行它，因此必须包含：触发范围、输入与前置条件、分步流程、工具/脚本用法、验收标准、错误回退、安全边界、所需资源与最小示例。

分层展开：文件通常分两部分。第一部分是 frontmatter（前置元数据：Markdown 文件开头用键值对声明的结构化字段），提供 `name`、`description`（写清何时用、何时不用）、`version`、`tags`，供选择器做快速匹配：

```markdown
---
name: generate-pdf
description: 生成符合排版规范的 PDF；当输入是 Markdown/文本且需要交付 PDF 时使用
version: 1.2.0
tags: [pdf, document]
---
```

第二部分是正文，至少要覆盖：①触发与不触发场景；②输入参数与前置条件（需要哪些文件、环境变量、依赖）；③可执行的分步流程，每步说明调用哪个工具/脚本、读取什么资源；④明确的验收标准（如"渲染后必须截图检查，文件须能被打开"），把"尽量做好"这类泛化表述替换成可检查的断言；⑤错误处理与回退路径；⑥安全边界（不做哪些危险动作、权限要求）；⑦最小可用示例。

举例：一个邮件发送 Skill 会写明输入收件人/主题/正文，流程为"校验地址→加载模板→渲染→发送→检查发送状态"，验收是"收件箱确实收到且未被误判为垃圾邮件"，出错时回退到人工发送。

注意与边界：要区分硬性规则与软性建议——硬性规则用"必须/禁止"，建议用"推荐"；Skill 应可测试（给一个回归样例）、可版本管理（Versioning：技能/工具接口变更时保持向后兼容的策略），并允许用户指令覆盖非安全性的默认值——安全边界默认不可覆盖。
- 关键点：SKILL.md=frontmatter 元信息+结构化正文；正文必须含触发范围、流程、验收、错误回退、安全边界；硬规则与建议要区分，且可测试、可版本化。

### Q45. 你常用或会设计哪些 Skills？
【深度回答】
先给结论：我会按场景把常用技能（Skill：可复用的任务操作手册与配套资源）分成"开发类"与"知识工作类"两类，面试时挑 3-5 个讲清输入、工具、流程和验收，而不是只罗列名称。

分层展开：开发场景常用的有：①代码库探索——输入是技术问题，流程是读目录结构→定位关键文件→输出带文件路径的解释；②测试与修复——输入是失败的测试名，流程是复现→读日志→定位改动→修复→重跑；③代码审查——输入是 diff（代码差异：变更前后的对比结果），流程是 diff→检查安全→按优先级输出问题；④日志排障——输入是错误关键字，流程是检索日志→找上下文→关联根因；⑤数据库迁移——输入是数据格式变更需求，输出是迁移脚本与回滚脚本。知识工作类则有 PDF/Word/PPT 生成、研究引用、会议纪要、项目管理等。设计原则是：每个 Skill 都要有明确的触发场景、稳定的验收标准和可测试的样例，避免写成放之四海皆准的空话。

举例：代码审查 Skill 我固定执行四步——先看 diff 范围是否合理；再跑静态检查与测试；重点查安全与权限问题；最后按"阻塞/建议/可选"分级输出，并附上每个问题的文件与行号。

注意与边界：Skills 不是越多越好，每个新增 Skill 都会增加选择器的负担与潜在误触发；建议从高频重复且步骤稳定的任务入手沉淀，并用回归评测确认它确实提升效果而不是增加噪声。
- 关键点：按"开发类+知识工作类"组织；面试讲 3-5 个并说清输入/工具/流程/验收；设计要有触发场景、验收标准与可测试性，宁缺毋滥。

### Q46. Skill 如何自动选择？如何防止选错？
【深度回答】
先给结论：技能（Skill：可复用的任务操作手册）自动选择的本质是一个基于"名称+描述+任务语义+环境能力"的匹配决策；防止选错要靠"互斥且具体的描述 + 优先级与人工澄清 + 前置条件复核 + 用精确率/召回率持续评测"四道防线。

分层展开：第一，选择信号。选择器（通常由模型或轻量分类器担任）读取当前任务与每个 Skill 的 `name`、`description`、`tags`，判断语义匹配度；同时考虑环境能力，比如机器上是否装了对应依赖、是否联网。第二，防止误触发。描述要互斥且具体，两个能力相近的 Skill 必须写清边界（"生成表格"与"操作已打开的 Excel"是不同的触发场景）；高风险 Skill 不应仅靠语义自动触发，应要求显式用户意图或审批；多个候选命中时按优先级裁决或向用户澄清：

```python
def select_skill(task, skills):
    candidates = [s for s in skills if match(task, s.description)]
    if not candidates:
        return None
    if len(candidates) == 1:
        return candidates[0]
    high = [s for s in candidates if s.priority > HIGH]
    return high[0] if high else ask_user(candidates)  # 冲突时澄清
```

第三，内部复核。即使被选中，Skill 正文第一步仍应验证前置条件（如输入文件存在、参数合法），不满足就拒绝或提示。第四，评测闭环。用一批"应该触发/不应触发"的样本统计精确率（Precision：选中结果中真正该触发的比例）与召回率（Recall：该触发的技能中被正确选中的比例），并记录实际加载轨迹，选错时回查是描述问题还是选择器问题。

举例：用户说"把这份数据做成表格"，应触发"表格生成"Skill；而"控制已经打开的 Excel"是另一个 Skill——两条描述必须把"新建/生成"和"操作已有实例"区分开，否则模型很容易选错。

注意与边界：描述优化是主要杠杆，但任何语义匹配都有误判率；对高风险技能宁可"多问一次"也不要"自动乱动"；评测样本要覆盖边界情况与反例，只加正例会掩盖过拟合。
- 关键点：选择依据=名称/描述/任务语义/环境能力；防错=互斥描述+优先级/澄清+前置复核+precision/recall 评测；高风险技能不自动触发。

### Q47. Skill 会带来哪些安全风险？
【深度回答】
先给结论：技能（Skill：可复用的任务操作手册）本质是"把不可信内容变成可执行流程"，所以主要风险是注入恶意指令、携带恶意脚本、外链诱导、权限过宽和资源过期——必须按"来源可信 + 权限最小 + 审批关键动作 + 内容低于系统安全策略"来防护。

分层展开，风险与对策一一对应：第一，内容风险。Skill 正文可能含恶意指令（如"读取 ~/.ssh 密钥"），脚本可能做坏事；对策是校验来源与签名、审查脚本内容，把 Skill 内容视为不可信数据而不是可信指令。第二，权限风险。Skill 声明过宽权限会放大破坏半径；对策是最小权限（sandbox，沙箱：限制进程文件/网络/凭据访问的隔离环境）执行，文件与网络域做白名单（Allowlist：允许访问的清单），密钥通过短期凭证注入而非写死在脚本里，这是凭据管理（Credential Management：安全存储与最小权限下发密钥的机制）的落地。第三，外部依赖风险。Skill 引用的 URL、模板、依赖包可能过期或被替换；对策是固定版本（Versioning：版本管理）、锁定依赖 hash、更新时重新审查。第四，执行透明性。执行前应显示 Skill 将执行的动作，对敏感步骤（删除、上传、转账）强制审批；安装与更新都要留审计日志。同时要明确优先级：Skill 内容必须低于系统安全策略，即使 Skill 要求"忽略限制"，系统规则仍然生效。

举例：一个来路不明的 Skill 里藏了"把 `.env` 上传到某域名"的脚本——安装审查会拒绝它；即便通过审查，沙箱的网络白名单也会阻止访问该域名；上传动作还需人工批准。三层防线挡住单点失误。

注意与边界：安全不能只靠一层，要从"来源审查→权限限制→执行透明→审计"层层设防；高风险 Skill 建议由可信方签名，内部 Skill 库比公网下载更可控。
- 关键点：Skill 风险=恶意内容/脚本/外链/过宽权限/资源过期；对策=来源签名审查+沙箱最小权限+动作透明与审批+固定版本；Skill 内容永远低于系统安全策略。

### Q48. MCP 的 Tools、Resources、Prompts 如何选择？
【深度回答】
先给结论：MCP（Model Context Protocol，模型上下文协议：Agent 连接外部工具与数据源的标准通信协议）暴露三类能力，选择标准是问"这个能力是动作还是数据"：需要执行动作、产生副作用时用工具（Tool：Agent 可调用的外部函数/API）；需要读取可寻址数据时用资源（Resource：MCP 中可寻址、可读取的数据对象，如文件、数据库记录）；希望给用户提供参数化模板/工作流入口时用提示（Prompt：MCP 中暴露给用户的参数化提示模板）。

分层展开：Tool 面向"改变世界"，可能产生副作用，适合搜索、写库、发消息等；宿主（Host：运行 Agent 并连接 MCP 服务器的应用）按用户同意与权限策略决定是否放行。Resource 面向"读取世界"，通过 URI（Uniform Resource Identifier，统一资源标识符：标识资源位置的字符串）寻址，适合文件内容、数据库查询结果、配置项等，Agent 可像查资料一样引用。Prompt 面向"提供入口"，是可复用、带参数占位符的模板，让用户以固定流程发起任务，模型将其展开为对话上下文。选型时要避免两个反模式：把纯读取包装成高权限工具（导致无谓副作用），以及把复杂写操作伪装成资源（绕过权限审查）。

举例：读取一个文件的内容用 Resource（`file:///config.json`）；删除文件用 Tool（`delete_file(path)`），必须走权限审批；给用户提供"生成周报"的入口用 Prompt 模板，让用户填项目名与周期。

注意与边界：同一能力可多形态暴露，但要遵循"最小惊讶"——读用 Resource、写用 Tool、入口用 Prompt；Host 还要做能力协商（Capability Negotiation：客户端与服务器交换各自支持的特性子集）和用户授权，不能因为工具出现在 MCP 列表里就自动信任调用。
- 关键点：选型口诀=读用 Resource、写用 Tool、入口用 Prompt；避免"纯读取高权限化"与"写操作伪装成资源"两种反模式；Host 负责协商、授权与权限策略。
