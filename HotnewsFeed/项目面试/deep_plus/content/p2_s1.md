# 《项目之外 · Agent 通用技术面试深度解析》
## 一、Agent 基础、Loop 与自主性（第 1-8 题）

### Q1. 什么是 AI Agent？它和普通 Chatbot、Workflow 有什么区别？

【深度回答】
直接结论：AI Agent（人工智能体：能感知环境、调用工具、自主规划并执行多步任务的程序）与 Chatbot（聊天机器人：以多轮对话输出文本为主的程序）、Workflow（工作流：按开发者预定义顺序执行的固定流程）的本质区别在于"决策权的位置"——Agent 把"下一步做什么"交给模型在运行时决定，而 Chatbot 只决定"怎么回答"，Workflow 根本不决策。

分层展开：
- 从能力看，Chatbot 是"输入问题→输出答案"的映射，核心是文本生成，通常没有工具、没有状态、没有副作用。Workflow 的每一步都由开发者写死，例如"先查库存→再算运费→最后下单"，固定、可预测、易测试，但遇到流程外的场景就失效。Agent 位于二者之上：它有明确目标，但路径不预枚举，每轮根据当前观察决定调用哪个工具、是否修改计划、何时结束。
- 从组成看，Agent = 模型（负责决策）+ 工具调用（Tool Calling / Function Calling：模型输出"要调用哪个函数及参数"的能力）+ 状态（State：跨轮共享的结构化数据）+ 反馈循环（Agent Loop：感知-推理-行动-观察的闭环）。它把 Chatbot 的"说"升级为"说 + 做 + 看结果再调整"。

例子：普通客服机器人只会回复"退款政策是 7 天内可退"；退款 Agent 则能查订单号、读取订单状态、校验是否符合政策、调用退款接口，最后查数据库确认退款记录真的落库，再回复用户。

边界与取舍：三者不是非此即彼，真实系统常是"外壳是 Workflow、内部某些节点是 Agent"，或"Agent 内嵌确定性校验"。选择标准是任务的可枚举程度与容错要求：路径固定选 Workflow，目标开放才选 Agent。同时 Agent 引入了不确定性、延迟和成本，必须配权限、评测与终止机制，否则会从"智能"变成"不可控"。

- 关键点：决策权归属不同是三者分界；Agent = 模型 + 工具 + 状态 + 循环；多数生产系统是 Agent 与 Workflow 的混合。

### Q2. 你了解 Agent Loop 吗？请描述一次完整循环。

【深度回答】
直接结论：Agent Loop（Agent 循环：感知-推理-行动-观察的闭环）是 Agent 运行的基本单位；一次完整循环由"读状态→模型决策→执行动作→更新状态"四阶段构成，并不断重复直到满足退出条件。

分层展开：
- ①感知：把系统指令、用户目标、历史消息、工具结果和当前状态组装成上下文（Context：模型这一次能看到的全部信息）。②推理：LLM（Large Language Model，大语言模型）判断这一步应直接回答，还是调用某工具并给出参数。③行动：由运行时（Runtime：承载并执行 Agent 循环的进程环境）而非模型本身执行工具，例如查库、写文件、调外部 API。④观察：工具结果（Observation：工具执行后返回的结果）回到上下文，模型据此更新状态，进入下一轮。
- 工程上，模型只输出"意图"，真正的执行、权限校验、超时、重试都在 Harness（运行外壳：把模型包装成可循环、可用工具、受约束执行的系统）里完成；每轮结束都要检查出口。

```python
while not should_stop(state):
    context = build_context(system, goal, history, tool_results)  # 感知
    decision = llm.decide(context)                                # 推理
    if decision.is_final_answer:
        break
    result = runtime.execute(decision.tool_call)                  # 行动
    state = state.update(decision, result)                        # 观察/更新
```

例子：用户让助手改行程。第 1 轮模型调天气工具，返回"下午下雨"；第 2 轮据此调日历工具把户外活动改到室内；第 3 轮确认更新成功后，模型判断目标达成，输出答复并退出。这就是两轮完整 Loop。

边界与取舍：Loop 不是跑得越多越好。没有出口的循环会烧掉 token 与费用；每轮重发全部历史会撑爆上下文，长任务需压缩与持久化。还要区分"模型说完成"与"环境真的完成"，后者以可验证的 outcome（结果：环境里真正发生的结果，而不是模型口头说成功）为准。

- 关键点：四阶段感知-推理-行动-观察；模型只决策、Harness 负责执行；每轮必须检查退出条件。

### Q3. ReAct 是什么？它与 Agent Loop 有什么关系？

【深度回答】
直接结论：ReAct（Reasoning + Acting：先推理后行动的提示范式）是把推理与行动交替组织的 Agent 决策策略；Agent Loop 是更广义的运行机制，ReAct 是 Loop 最常见的一种实现方式。

分层展开：
- ReAct 让模型每轮交替产生 Thought（推理：对当前情况的判断和下一步打算）、Action（行动：决定调用哪个工具及参数）、Observation（观察：工具执行后返回的结果），并把上一轮的 Observation 作为下一轮推理输入，形成"想→做→看→再想"的闭环。相比 Chain-of-Thought（CoT，思维链：让模型先输出中间推理再给答案的提示技术），ReAct 的关键升级是把推理与外部真实反馈耦合：模型不必只靠内部记忆猜，可以查证、试错、修正。
- 与 Loop 的关系：Loop 属于"运行机制层"，负责状态流转、工具执行、停止条件、权限与预算管理；ReAct 属于"决策策略层"，负责模型内部怎么组织思考与行动。同一个 Loop 里可以装 ReAct，也可以装 Plan-and-Execute 等其他策略。工程上通常不把完整思维链暴露给用户，而是保留结构化的 tool_call、observation 和简短决策摘要，便于调试与审计。

例子：查航班时，模型先 Thought"需要查北京到上海的航班"，Action 调 search_flights；工具返回"最早 7:00"，成为下一轮 Observation；模型再 Thought"日期冲突，需改期"，Action 调另一个工具。整条链是 ReAct，外层负责循环、重试、超时的机制是 Loop。

边界与取舍：ReAct 的缺点是"走一步看一步"步子碎、长任务易迷失方向，通常要叠加规划、记忆或 Plan-and-Execute。同时必须控制 Action 的权限范围，防止模型基于被污染的 Observation 执行危险动作。

- 关键点：ReAct = Thought/Action/Observation 交替；Loop 是机制、ReAct 是策略；工程上隐藏完整思维链、保留结构化轨迹。

### Q4. Agent Loop 的退出条件应该怎么设计？

【深度回答】
直接结论：退出条件不能只靠模型说"完成了"，应设计一组多层次、可验证的终止信号，覆盖"任务完成、无需继续、需要人工、超限、无进展、异常"六类场景，并用确定性代码兜底。

分层展开：
- 正常完成类：①任务完成——以环境真实 outcome（结果：环境里真正发生的结果，而不是模型口头说成功）为准，例如测试通过、订单已写入数据库、目标文件已生成；②模型不再请求工具，且已给出满足目标的最终答复。
- 控制类：③达到硬性上限：max_steps（最大步数）、deadline（截止时间）、token/cost budget（令牌/费用预算）；④工具返回终止状态（如搜索无结果、API 明确拒绝）。
- 干预类：⑤需要用户确认，即 HITL（Human-in-the-Loop：关键步骤暂停等待人工确认），例如高危写操作前挂起；⑥重复动作或无进展；⑦策略违规（违反系统安全规则）或不可恢复异常（凭据失效、解析失败）。
- 工程实践：退出判定 = 确定性检查器 + 模型自判。检查器用代码判断 outcome、步数、预算，不受模型幻觉影响；模型自判负责"目标语义是否满足"。退出状态（success/needs_human/aborted）写入状态机，便于恢复与审计。

```python
def should_stop(state):
    if verify_outcome(state.goal):    return "success"      # 环境验证
    if state.steps >= MAX_STEPS:      return "max_steps"
    if elapsed() > DEADLINE:          return "deadline"
    if cost_spent() > COST_BUDGET:    return "budget"
    if needs_human_approval(state):   return "needs_human"  # HITL
    if is_stalled(state):             return "stalled"
    if violates_policy(state):        return "policy_violation"
    return None  # 继续循环
```

例子：代码 Agent 说"修好了"不算结束，必须 pytest 通过、且 git diff 确实改了目标文件才算 outcome 达成；连续三次同样修复仍失败，判定无进展并转人工。

边界与取舍：条件太宽松会烧钱失控，太严格会过早终止任务。步数与预算上限是"硬保护"，防止检测器失效；"无进展"判定要容忍合理探索期，避免把正常试错误判为死循环。

- 关键点：outcome 优先于口头声明；六类退出信号缺一不可；确定性检查器兜底 + 模型自判补充。

### Q5. 如何检测 Agent 陷入死循环或无效循环？

【深度回答】
直接结论：检测的核心是"留痕 + 比较"——为每轮动作保留结构化痕迹，通过比较工具、参数、状态哈希与进度指标是否重复来判定 stalled（停滞：反复做相同动作却没有进展），并用硬性上限兜底。

分层展开：
- 留痕：每轮记录 action（动作名）、arguments（参数）、observation 摘要和状态哈希（state hash：把状态序列化后哈希成固定字符串，用于快速比较）。有了轨迹才能判断"是否重复"。
- 判定规则：①重复动作——连续 N 轮相同工具、相同参数，如连续三次请求同一 URL 都返回 403；②错误不变——同样的异常持续出现；③状态哈希周期性重复——状态回到之前某点，说明在绕圈；④目标指标无改善——通过测试数、已修改文件数等长时间不变。

```python
def detect_stall(trace, window=3):
    recent = trace[-window:]
    if all(t.action == recent[0].action and t.args == recent[0].args
           for t in recent):
        return "repeat_action"     # 动作与参数完全重复
    if len({t.state_hash for t in recent}) < 2:
        return "state_cycle"       # 状态周期性重复
    if not progress_improving(trace):
        return "no_progress"       # 目标指标无改善
    return "ok"
```

- 处理策略按严重程度递进：注入错误摘要（"你刚才三次都 403"）→ 换策略或换模型 → 回滚到最近 checkpoint（检查点：可恢复执行的状态快照）重试 → 请求人工输入 → 终止任务。
- 兜底：设置硬性的 step、时间和费用上限。检测器本身也可能失效（哈希碰撞、日志缺失），硬上限是最后防线。

例子：爬虫 Agent 连续五次调用同一个 URL 都返回 403，参数相同、错误码不变，就是典型死循环信号；应停止重试，改为换凭据、换 URL 或请求人工，而不是继续第六次。

边界与取舍：阈值要平衡误报与漏报。过小会把"正在探索多种方案"误判为死循环；过大会让无效循环白烧预算。因此"无进展"判定通常结合进度指标，而不只看动作重复。

- 关键点：动作/参数/状态哈希三重留痕；重复判定 + 硬性上限双保险；恢复优先回 checkpoint 而非从头跑。

### Q6. Agent 的 planning 有哪些方式？

【深度回答】
直接结论：planning（规划：把目标拆成子目标序列并安排执行顺序）没有银弹，常见方式可归为五类：即时 ReAct、先计划后执行、分层任务树、图搜索、动态重规划；选择依据是任务长度、可逆性与环境稳定性。

分层展开：
- 即时决策（ReAct）：不做预计划，走一步看一步。适合短小、可逆、探索型任务，灵活省 token，但长任务易迷失。
- 先计划后执行（Plan-and-Execute：先生成完整计划再逐步执行）：先生成里程碑列表，再逐步执行并在里程碑间检查。适合长任务，计划可审查、可对齐；但计划可能过早失效、浪费规划 token。
- 分层任务树（Hierarchical Planning：把目标递归拆成子任务的分层结构）：高层管方向、低层管执行，天然支持并行与分工，适合大规模可分解任务。
- 图搜索（Graph Search：把状态建模成图，用 BFS/DFS 等算法找路径）：适合状态空间明确、可枚举的规划问题，但真实开放环境很难建模。
- 动态重规划（Dynamic Replanning：执行中定期检查环境变化并重新规划剩余步骤）：类似滚动窗口，适合外部变化大的场景。

例子：改一个变量直接用 ReAct 即可；跨 20 个文件的重构应先生成里程碑（接口定义→模块 A→模块 B→集成测试），每完成一个验证一次，发现需求变更再局部重规划，而不是开头就把 100 步全部展开。

边界与取舍：计划不是越详细越好——过早展开所有细节既浪费 token，又会在环境变化后迅速失效；完全没有计划的 ReAct 又缺少方向。常用折中是"粗粒度计划 + 细粒度执行"：高层有里程碑，底层仍用 ReAct 走。

- 关键点：五类方式各有适用场景；计划粒度与任务长度、环境稳定性匹配；"粗计划 + 细执行"是常用折中。

### Q7. 什么时候不应该使用 Agent？

【深度回答】
直接结论：当任务"路径固定、规则明确、要求确定性或低延迟"时，不应该使用 Agent；普通函数、状态机（State Machine：状态与转移完全确定的执行模型）或 Workflow 更合适时，就别硬套 Agent。

分层展开：
- 应避免的场景：①规则固定、可预先枚举——CSV 转 PDF、定时报表、格式化通知，用脚本一步到位；②低延迟高吞吐——Agent 每轮都要调 LLM，延迟和成本远高于确定性代码，不适合在线高并发路径；③结果必须确定——交易计算、格式解析要求 100% 可复现，模型不确定性不可接受；④单次检索+生成可解决——一次 RAG 查询加一次生成就够的问题，引入自主 Loop 是过度设计。
- 隐性代价：Agent 会带来三类成本——延迟（多轮模型调用）、token 成本、不可预测性与安全面扩大（工具越多攻击面越大）。只有当步骤难以预先枚举、需要动态选择工具、处理开放环境时，收益才可能覆盖这些成本。
- 决策方法：问三个问题——步骤能预先枚举吗？错误可容忍吗？需要外部动态反馈吗？三个都否，就不用 Agent。

例子：每天固定把 CSV 转成 PDF 的批处理，用一段 20 行的 Python 脚本最合适；让 Agent 每次重新"理解需求、规划步骤、调用工具"不仅慢，还可能把列名认错。反之，"根据邮件内容自动回复并安排会议"这类开放任务用 Agent 才有意义。

边界与取舍："不用 Agent"不等于"不用 AI"。单次 LLM 调用、普通函数、带固定分支的 Workflow 都介于两者之间。成熟做法是"默认用最简方案，评测证明复杂度有收益再升级"，而不是"默认上 Agent"。

- 关键点：确定性/低延迟/可枚举场景用脚本或 Workflow；Agent 的代价是延迟、成本、不可预测性；决策看"能否预枚举、是否需要动态反馈"。

### Q8. 怎样衡量一个 Agent 的自主性？自主性越高越好吗？

【深度回答】
直接结论：自主性（autonomy：无需人工干预完成任务的属性）应从"目标拆解、工具选择、路径规划、错误恢复、运行时长、人工确认频率"六个维度衡量；它不是单一等级，更不是越高越好——成熟设计追求"与风险匹配的最小必要自主性"。

分层展开：
- 六个衡量维度：①目标拆解——接受完整目标还是只能执行单步指令；②工具选择——自主挑选工具还是由外部指定；③路径规划——自己排步骤顺序；④错误恢复——失败后自行重试/换方案还是立即求助；⑤运行时长——能连续自主工作多久（分钟级 vs 小时级）；⑥人工确认频率——单位任务内需要多少次 HITL（Human-in-the-Loop：关键步骤暂停等待人工确认）。
- 自主性与风险必须匹配：读操作（查文档、搜网页、读代码）可高自主、零确认；高风险写操作（删生产库、对外转账、发邮件、部署上线）必须收紧权限并强制 HITL；中等风险（改代码、写文件）可设自动校验门槛，不过才转人工。
- 工程实践：把自主性做成"风险分档 + 工具白名单"，而非一把开关。每个工具注册时声明风险等级，运行时按等级决定是否暂停：自动执行（只读/可逆）、需审批（写/外部副作用）、禁止（高危/不可逆）。

例子：读公开网页可全自动完成；而"删除生产数据库"这一动作，即使模型自信地调用 drop 接口，Harness 也应拦截并挂起等待人工确认——系统规则高于模型判断。

边界与取舍：自主性过高会放大错误爆炸半径（blast radius：单次错误或攻击能造成的最大影响范围），一次幻觉可能导致不可逆损失；过低则频繁打断，把 Agent 退化成"人步步喂"的工具。正确做法是"高自主只给低风险任务，高风险任务永远保留人工兜底"，并用评测持续校准各风险等级的确认阈值。

- 关键点：六维度衡量自主性；自主性要与风险匹配而非无限放权；用风险分档 + 工具白名单实现分级自主。
