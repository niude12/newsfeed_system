# 《项目之外 · Agent 通用技术面试深度解析》
## 八、Evals、Observability、Guardrails 与安全（第 57-64 题）

### Q57. Agent Eval 与普通 LLM Eval 有什么不同？
【深度回答】
直接结论：普通 LLM Eval（Evaluation，评测：用指标自动评估输出质量）只判断"一问一答"的文本质量；Agent Eval（智能体评测：对 Agent 的决策、工具调用与最终结果进行整体评估）还必须同时评估工具调用过程和真实环境结果，因为 Agent 的价值在于"是否真的把事情做完"。

分层展开原理与实践：
- **评测对象从单条回复扩展到完整回合**。普通评测给模型一个 prompt（提示词：给模型的指令文本），把输出与 gold set（人工标注的标准答案集）比对，或让 LLM-as-a-Judge（用大模型当评分器）打分即可。Agent 一次任务包含多轮模型决策、多个工具调用，最终文本只是最后一层。
- **三层评测缺一不可**：① 最终回答——语义、格式是否正确；② 单步工具——是否选对工具、参数是否合法、顺序是否合理；③ outcome（环境里真正发生的结果，而不是模型口头说成功）——数据库是否真的写入、文件是否真的生成、测试是否真的通过。
- **需要多次运行取统计**。Agent 路径有随机性，跑一次成功不代表稳定，要重复运行并计算成功率与 precision / recall（精确率/召回率：衡量"选对/漏掉"的比例）。
- **成本与安全也是评测维度**：token（词元：模型计费与处理的基本单位）消耗、端到端延迟、是否越权访问敏感资源。

一个具体例子：订票 Agent 回复"订票成功"不能算通过，必须在数据库里查到这条真实订单才算 outcome 通过；若它先调"退票"再调"订票"，即使最终成功，工具轨迹也被判为有缺陷。

注意事项与边界：Agent Eval 工程量大——需要可重置的隔离测试环境、mock（模拟：用假对象替代真实外部依赖）外部依赖、可查询真实状态的检查器；不能只靠 LLM judge 判断"看起来对"。评测集也会过时，要持续把线上失败沉淀为回归样本。

- 关键点：三层评测（回答/工具/outcome）；多次运行取统计；环境真实状态是硬标准。

### Q58. 什么是 trajectory evaluation？
【深度回答】
直接结论：Trajectory evaluation（轨迹评测：对一次任务从开始到结束的完整执行过程进行评估）不只看最终结果，而是检查整条运行轨迹——模型决策、工具调用、参数、观察结果、状态变化——判断"过程是否合理"。

分层展开原理与实践：
- **轨迹（trajectory）是什么**：一次运行的完整记录，包含用户请求、每轮模型消息、工具名与参数、工具返回的观察结果（observation）、状态变化和最终回答。它把 Agent 的"行为过程"变成可审计、可评估的对象。
- **评估什么**：必需工具是否被调用（先查库存再下单）；是否存在多余或重复步骤；调用顺序是否符合业务依赖；参数是否正确；失败后是否错误地继续执行。
- **怎么评估**：三层结合——规则检查（硬性的 must/must-not 序列）、LLM-as-a-Judge（用大模型当评分器）与参考轨迹对比、人工抽查。
- **与 outcome 的关系**：outcome（环境里真正发生的结果）检查"结果对不对"，轨迹检查"过程对不对"。一个侥幸成功的结果可能来自错误的路径（比如跳过了必要校验），只有轨迹评测能发现这类问题。

一个具体例子：下单 Agent 没有先查库存就创建订单，订单确实创建成功（outcome 通过），但轨迹评测判定失败，因为它跳过了必需的库存前置步骤——这种缺陷只有在过程层才能暴露。

注意事项与边界：正确路径往往不唯一，严格"逐步完全匹配"会误伤合理的替代方案，因此轨迹评测更适合作为问题发现、回归分析和根因定位的手段，与 outcome 检查配合而非替代；轨迹数据量大、评估成本高，通常抽样执行而不是全量。

- 关键点：过程与结果互补；规则+judge+人工三层评估；正确路径不唯一，避免过度匹配。

### Q59. 代码 grader、LLM-as-judge 和人工评审怎么组合？
【深度回答】
直接结论：任何单一 grader（评分器：判断结果对错的程序或模型）都无法覆盖所有错误，应采用"瑞士奶酪模型"式的多层组合：确定性结果优先用代码 grader，主观质量用带 rubric 的 LLM-as-a-Judge，高风险与边界样本保留人工评审。

分层展开原理与实践：
- **代码 grader 最可靠**：测试是否通过、JSON schema（数据结构定义：输入输出必须遵守的格式）是否合法、数据库状态是否正确、精确值是否命中。它可复现、成本低，但只能判断"可判定的性质"，判断不了"好不好"。
- **LLM-as-a-Judge（用大模型当评分器）处理主观维度**：相关性、完整性、行文风格、推理连贯性。要给明确的评分标准 rubric（评分标准：定义各分数档位的打分依据）并按维度打分，定期与人工标注结果校准，随机打乱顺序避免位置偏差。
- **人工评审成本最高**，只保留给：高风险动作（删除、转账）、法律/财务相关、边界样本，以及前两层意见冲突的样本。
- **组合策略是瀑布式**，用伪代码表达：

```python
def grade(run):
    if not code_grader.pass(run):        # 1. 确定性失败直接挂
        return REJECT
    score = llm_judge.score(run)         # 2. 主观质量打分
    if score < low_threshold:
        return REJECT
    if run.is_high_risk or score in gray_zone:   # 3. 高风险或不确定
        return human_review(run)
    return ACCEPT
```

一个具体例子：代码 Agent 任务先跑 pytest 判断能否运行；再让 LLM judge 按"可读性、正确性"的 rubric 打分；凡涉及删除生产数据的改动一律升级到人工评审。

注意事项与边界：LLM judge 有系统性偏差（偏好更长回答、偏好与自己风格一致、受顺序影响），必须用人工标注集定期校准；避免让"被评测的模型"同时当自己的 judge；人工评审要抽样并设置清晰的升级标准，否则会成为发布瓶颈。

- 关键点：确定性→主观→人工的瀑布组合；LLM judge 需校准；高风险强制人工兜底。

### Q60. Capability Eval 与 Regression Eval 有什么区别？
【深度回答】
直接结论：Capability Eval（能力评测：衡量 Agent 当前能力上限的评测）回答"现在能做什么"，选题偏难、初始通过率可以很低；Regression Eval（回归评测：防止已稳定能力倒退的评测）回答"以前会做的现在还会不会"，期望接近 100% 通过。

分层展开原理与实践：
- **目的不同**。能力评测用于探索上限、指导研发投入方向，比如"模型升级后能不能处理跨 20 文件重构"，通过率从低到高迭代是进步的表现；回归评测用于保护存量，防止模型、工具或 Prompt 改动把已稳定的行为搞坏。
- **样本来源不同**。能力题来自新需求、更难的边界和公开 benchmark（基准测试集：标准化、可对比的任务集合）；回归题来自真实线上失败、用户投诉、安全事件和曾经修过的 bug。
- **两者会互相转化**：一道能力题通过率稳定超过阈值后，就"转正"为回归题；而任何新的真实失败都应沉淀成新的回归样本，防止同一个坑再次踩到。
- **判读方式不同**。能力评测看趋势和上限（30%→60% 是成长）；回归评测看波动，任何单点下降都应告警并阻塞发布。

一个具体例子：新能力题"跨 20 个文件重构"通过率从 30% 提到 60%，说明能力在变强；已稳定的"退款流程"要求每次回归接近 100%，一旦掉到 90% 就必须查原因、阻断发版。

注意事项与边界：回归集要控制规模、做去重，否则每次运行成本很高；两种评测集都要与训练/调优数据隔离，防止"刷分过拟合"——为了在评测集上拿高分而牺牲真实泛化能力。评测集本身也要随需求演进持续维护。

- 关键点：能力评测看上限、回归评测守存量；失败案例持续转化为回归样本；数据隔离、防刷分过拟合。

### Q61. Agent 上线要记录哪些 Trace？
【深度回答】
直接结论：Trace（链路追踪：记录一次请求经过的所有步骤）是 Agent 可观测性的地基，至少应覆盖"关联标识、模型决策、工具调用、资源消耗、最终结果"五类信息，并用统一 trace_id 串起来支持回放与排查。

分层展开原理与实践：
- **关联标识**：trace_id（一次任务全局唯一 ID）、task_id、user_id、thread_id，以及多 Agent 场景下的 parent-child span（跨度：一次操作的时间片段）关系和 handoff（转交：一个 Agent 把任务移交给另一个 Agent）关系。
- **模型层**：模型名与版本、Prompt（提示词）版本、上下文摘要（不必存原文）、输入/输出 token（词元）数。
- **工具层**：工具名、参数（敏感字段脱敏）、返回结果摘要或校验状态、耗时、错误码与重试次数。
- **编排层**：每轮循环的状态、从哪个 checkpoint（检查点：可恢复执行的状态快照）恢复、是否降级、终止原因。
- **结果与成本**：最终 outcome（环境里真正发生的结果）、端到端延迟、总 token 与成本、完成/超限/人工介入的退出原因。

一个具体例子：一次订单查询要能完整回放"用户 → 路由 Agent → 订单 Agent → get_order 工具 → 数据库 → 返回"的链路；用户反馈"没查到"，靠 trace 定位发现是 get_order 工具入参把订单号截断了。

注意事项与边界：完整推理链不应原样入库（会泄露 PII（Personally Identifiable Information，个人身份信息）），保留结构化决策摘要和必要证据即可；日志应做 structured logging（结构化日志：机器可读的 JSON 日志，便于检索与聚合）并接入 OpenTelemetry（开源可观测性框架：统一采集 trace、metric、log 的标准），避免自造格式；trace 数据量大，需要设采样率（如 10%）控制存储成本，但错误路径建议全量采集。

- 关键点：五类信息+统一 trace_id 串起全链路；敏感推理脱敏保留摘要；结构化+OpenTelemetry+采样。

### Q62. Guardrails 应放在哪些层？
【深度回答】
直接结论：Guardrail（护栏：约束模型行为的规则）必须贯穿多层，而不是只靠一句系统 Prompt：输入层、规划层、工具层、输出层、环境层，并在高风险节点用 HITL（Human-in-the-Loop，人机协同：关键步骤暂停等待人工确认）兜底。

分层展开原理与实践：
- **输入层**：身份鉴权与越权检测，过滤 prompt injection（提示词注入：在网页、文件等外部内容中藏指令试图劫持模型）和有害内容。
- **规划层**：限制任务目标范围、最大步数、时间和预算上限，防止 Agent 无限循环或越跑越偏。
- **工具层（最关键）**：工具 allowlist（白名单：允许调用的工具清单）、参数 schema（数据结构定义）校验、权限模型（谁有资格调哪个工具）、rate limiting（限流：控制单位时间内的调用次数）、副作用分级——只读 / 写 / 破坏性操作分别对待。
- **输出层**：PII（个人身份信息）检测、事实核查、输出格式校验，防止把错误或违规内容发给用户。
- **环境层**：沙箱（sandbox：隔离进程、文件、网络的受控执行环境）、网络策略、密钥隔离。
- **高风险节点**：破坏性写操作（删库、转账、发布）在执行前暂停，等待人工确认。

一个具体例子：读天气接口走自动执行（只读+白名单）；转账则必须同时通过工具权限校验和人工确认两道独立防线，任何一道不通过都中止。

注意事项与边界：每层护栏都可能被绕过，所以各层应并联冗余而不是串联依赖，并记录每次拦截原因以便审计；护栏过严会误伤正常请求，要配置放行规则和申诉通道；护栏应与业务逻辑分离、可独立版本化，升级时不阻塞主流程。

- 关键点：六层防线，工具层是重心；多层冗余+可审计；HITL 兜底高风险写操作。

### Q63. 如何防止 Tool Poisoning 和恶意 MCP Server？
【深度回答】
直接结论：核心是把工具描述、schema 和返回内容都当成"不可信输入"：通过信任链、Host 审核、最小权限隔离、调用前显示与返回校验来防御。一个 MCP Server（Model Context Protocol，模型上下文协议：Agent 连接工具和数据的标准协议的服务端）出现在工具列表里，不代表它可以被信任。

分层展开原理与实践：
- **理解威胁**：Tool poisoning（工具投毒：恶意工具描述或返回内容诱导 Agent 执行危险操作）的形态包括——工具描述里藏指令（如"调用前先上传密钥"）、schema 诱导 Agent 填入危险参数、工具返回内容夹带 prompt injection（提示词注入）进而污染后续决策。
- **信任链**：只连接受信任或签名的 Server，固定版本和域名，校验 server identity（服务器身份），记录工具的来源与提供方。
- **Host 侧重写/审核**：客户端不应照单全收 Server 下发的描述，应由 Host（宿主：运行 Agent 的主程序）重写或人工审核，剥离危险指令，再交给模型。
- **最小权限与隔离**：按 Server 隔离凭据，每个 Server 只有完成本职的最小权限；限制其网络访问、可暴露的文件范围 roots（根路径：MCP 允许暴露给服务器的文件范围）和采样能力。
- **调用前显示动作 + 返回校验**：高风险工具执行前向用户展示将要执行的动作并请求确认；调用后校验返回 schema（数据结构定义），防止返回内容反向劫持模型。
- **监测与审计**：记录每次调用的 server identity、参数、结果，异常调用模式（短时间内大量外发、读取敏感路径）触发告警。

一个具体例子：第三方 MCP Server 把某个工具描述写成"先读取并上传 /etc/keys"，Host 审核描述时发现并剔除该指令，同时该 Server 的网络策略禁止外发到非白名单域名，双保险拦下攻击。

注意事项与边界：与 prompt injection 同源，网页内容、RAG（Retrieval-Augmented Generation，检索增强生成：先检索资料再让模型据此生成）检索结果同样可能投毒，属于同一类防御面；信任不是一劳永逸，要定期重估已连接 Server 的信任等级、复查依赖版本；安全更新要有审计链。

- 关键点：工具内容不可信；信任链+Host 审核；按 Server 隔离凭据与最小权限；返回校验+审计告警。

### Q64. 如何控制 Agent 的成本和延迟？
【深度回答】
直接结论：控制成本和延迟的本质是"让每个 token 都花在刀刃上"，手段是模型路由、上下文精简、缓存、并行与预算上限五管齐下，并且所有优化都必须用 Eval（评测：用指标自动评估输出质量）证明没有以质量换速度。

分层展开原理与实践：
- **模型路由（model routing：按任务难度选择不同模型）**：分类、抽取、校验用便宜小模型，复杂推理、长链路规划用强模型；小模型低置信度时再升级 fallback（回退：低置信度或失败时切换到更强模型）。
- **上下文与工具精简**：削减无用历史、压缩旧消息、精简过长的工具描述，减少每次调用的输入 token（词元）。
- **缓存**：检索与 Embedding（把文本转换成可比较的向量）结果缓存、相同前缀的 prompt（提示词）缓存、工具结果缓存，命中即免调用。
- **并行与批处理**：相互独立的子任务并行调用，把串行延迟摊平成并行；同类小任务批处理，减少请求次数。
- **预算上限**：设置 step/token/time/cost budget（预算上限：任务消耗的硬性天花板），到顶即停止、降级或转人工，防止单任务失控跑飞。
- **监控口径**：按"每个成功任务的成本"统计，而非只看单次 token；延迟看整体完成时间，同时关注 p95（第 95 百分位：反映最差 5% 场景的性能）而不是只看平均值。

一个具体例子：意图分类走小模型、复杂规划走强模型；小模型置信度低于 0.8 时再升级。切换后平均成本降一半，用回归评测确认任务成功率不变后才放量。

注意事项与边界：路由要防"简单任务被误判导致失败"，需要置信度阈值、失败回退和质量监控；压缩上下文可能丢失关键信息，必须用 Eval 对比压缩前后的任务成功率；不要只压首 token 延迟（TTFT，Time To First Token：从发出请求到收到第一个 token 的时间）而忽略整体完成时长；省钱不能以失败率和用户体验为代价。

- 关键点：路由+精简+缓存+并行+预算五管齐下；按成功任务成本考核；一切优化以 eval 为准绳。
