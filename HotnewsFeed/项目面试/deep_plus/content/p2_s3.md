# 《项目之外 · Agent 通用技术面试深度解析》
## 三、Harness、Runtime 与长任务工程（第 17-24 题）

### Q17. 你了解 Agent Harness 吗？它是什么？
【深度回答】
先给结论：Harness（运行时外壳：托管 Agent 循环、工具与上下文管理的执行框架）是围绕模型（Model：负责推理与文本生成的神经网络）搭建的"运行环境 + 管理系统"。模型只负责判断，Harness 负责把单次推理扩展成"感知→决策→行动→反馈"的多轮闭环，让一个 Agent（智能体：能自主规划决策并调用工具完成目标的模型系统）从"只会聊天"变成"能干活"。

分层展开其职责与组成：
第一，职责边界。模型是纯函数式的单次推理，没有记忆也没有工具；Harness 负责把任务和上下文组织好喂给模型，接收模型的决策（直接回答或调用工具），执行工具，把结果回传模型，并管理循环、权限、状态、错误和日志。它决定了模型"能不能干活、能干什么活、干砸了会怎样"。
第二，核心组件。循环驱动器负责迭代直到满足退出条件（任务完成、达到 max_steps、deadline 或 timeout（超时：对单步或整体执行的时限））；工具注册表把工具名称和参数 schema 暴露给模型并调度执行；执行器/沙箱（executor/sandbox：隔离代码运行的受限环境）约束动作范围；状态与记忆模块保存跨轮数据；Trace/Eval 采集器（Trace：一次任务从头到尾的完整调用轨迹；Eval：用固定样本集量化评估 Agent 表现的方法）记录每轮输入输出供调试与评测。整个循环由 event loop（事件循环：异步任务调度的核心）驱动，避免阻塞等待。其骨架可表示为：
```python
while not done and budget.remaining():
    ctx = harness.assemble(task, state, tool_docs)   # 组织上下文
    decision = model.generate(ctx)                    # 模型判断
    if decision.is_tool_call():
        obs = harness.execute(decision.tool, decision.args)  # 执行工具
        state = harness.update(state, obs)            # 更新状态
    else:
        return decision.answer                        # 显式出口
```
第三，为什么重要。同一个模型放进不同 Harness，实际能力可能差很多——工具描述是否清晰、日志是否可读、状态能否恢复、权限是否合理，都直接决定模型表现。

举例：同一个模型放进只有聊天框的程序里只是一个助手；放进带终端、文件读写、测试运行、权限控制和完整 Loop 的 Harness 里，才成为能自主修代码的 coding Agent。

注意与取舍：Harness 的权限设计决定"错误半径"，过宽引入安全风险，过窄让 Agent 寸步难行；评测 Agent 时测的其实是"模型 + Harness + 工具 + 环境"的组合，不能把能力差异都归因于模型。
- 关键点：Harness 是执行外壳而非模型本身；它决定工具、权限、状态与可观测性；Agent 评测测的是组合系统而非单一模型。

### Q18. Model、Agent、Harness、Framework 四者如何区分？
【深度回答】
先给结论：四者是"内核→主体→外壳→生产工具"的层级关系：模型（Model：负责推理与文本生成的神经网络）只负责预测，Agent（智能体：能自主规划决策并调用工具完成目标的模型系统）负责有目标地行动，Harness（运行时外壳：托管 Agent 循环、工具与上下文管理的执行框架）是运行 Agent 的具体外壳，Framework（框架：提供构建 Harness 与 Workflow 的抽象组件库）用于批量搭建这类外壳。

分层区分：
第一，Model 是最底层。它只做"给定上下文、预测下一段文本"，无记忆、无工具、无目标，同一个模型可以被任何系统调用；模型是纯函数，不产生持续行为。
第二，Agent 是行为主体。它由模型 + 明确目标 + 可调工具 + 运行状态 + 决策循环共同构成，具备"自己决定下一步"的能力；离开循环和工具，模型就退化成聊天接口，不再是一个 Agent。
第三，Harness 是具体运行环境。它把模型、工具、状态、权限、日志组织在一起，并承载运行时（Runtime：承载 Agent 代码执行的环境）策略——超时、重试、并发与资源限制。它决定 Agent 每一轮能看到什么、能做什么、出错了怎么处理；相同模型放进不同 Harness，行为差异可能很大。
第四，Framework 是抽象层。它不直接运行某个 Agent，而是提供节点（node）、边（edge）、状态（state）、持久化、流式输出等可复用组件，让你用声明式代码搭建出多种 Harness 与 Workflow，从而在不同产品间复用工程经验。

举例：GPT 是模型，Codex 是带工具、沙箱和运行时循环的 Agent 产品，LangGraph 是搭建这种运行流程的框架——三层可以配合使用，职责却完全不同。

注意与边界：实际产品往往边界模糊，例如 Agent 库可能内置默认 Harness，Framework 也可能自带运行时；面试时点明"Agent 评测测的是模型 + Harness + 工具 + 环境"的组合结论，能体现对系统复杂性的理解，避免把环境差异误判成模型差异。
- 关键点：模型只推理、Agent 有目标地行动、Harness 是运行外壳、Framework 是构建工具；同模型换 Harness 表现会变。

### Q19. 一个好的 coding-agent Harness 应包含什么？
【深度回答】
先给结论：一个好的 coding-agent Harness 的总目标是让"应用、测试和运行状态"对 Agent 可观察、可操作、可验证——核心不是功能堆叠，而是让模型每一步都不用猜。

分层展开应包含的能力：
第一，感知与探索层。代码库检索（语义搜索 + 符号定位）、文件浏览与编辑、Git diff 与提交历史查看，让 Agent 先"读得懂"项目再动手。
第二，动作与验证层。shell/终端、编辑器、测试与静态检查（pytest、lint、type check）、构建和重启应用，让 Agent 能执行动作并立刻看到结果——"改完就跑测试"应当成为工作流的一部分。
第三，控制与安全层。网络与文件权限、隔离工作区（沙箱：隔离代码运行的受限环境）、环境变量与密钥管理，把动作限制在安全范围内。
第四，规划与韧性层。任务计划、进度记录、失败恢复、checkpoint（检查点机制：可恢复执行的状态快照）、剩余工作清单、可重启的开发环境，支撑跨多轮甚至跨会话的长任务；环境漂移后能从中断处继续，而不是从头再来。
第五，质量层。日志/指标采集、最终自检（让 Agent 交付前自行验证），必要时引入独立 review Agent 做第二意见，避免"自我验收 = 自我背书"。

举例：Agent 改完代码后必须自己运行 `pytest`、读取失败日志、修复后再次测试，直到通过——"改完就交差"在好的 Harness 里不被接受，验证动作本身就是流程的一部分。

注意与取舍：工具并非越多越好，描述模糊或互相重叠的工具会让模型选错；每一步验证都增加延迟与成本，要在"可验证性"和"执行效率"之间平衡；长任务尤其依赖 checkpoint + 可重启环境，否则一次环境漂移就前功尽弃。
- 关键点：可观察、可操作、可验证是总纲；工具要高内聚、描述清晰；长任务依赖 checkpoint 与自检闭环。

### Q20. 为什么 Harness 会显著影响 Agent 能力？
【深度回答】
先给结论：模型只能依据"它看到的上下文 + 工具返回的反馈"行动，而 Harness（运行时外壳：托管 Agent 循环、工具与上下文管理的执行框架）正好决定这两者的质量，所以同等模型在不同 Harness 里能力差异极大。这是 Harness Engineering（Harness 工程：通过优化运行外壳来放大模型能力的实践）的核心命题。

分层展开原因：
第一，信息能见度决定决策质量。如果工具描述模糊，模型会选错工具；如果日志不可读、测试难启动，模型只能靠猜；如果状态无法恢复，模型会重复劳动。好的 Harness 把环境"变得可读"：结构化日志、可一键启动的实例、清晰的错误堆栈，让模型像工程师一样定位问题。
第二，反馈回路决定迭代效率。模型是"以反馈为燃料"的：每轮拿到与当前目标最相关的结果，才能修正下一步。Harness 负责在每轮只呈现最相关反馈，避免上下文被无关信息稀释；反馈太稀疏，模型就退化成盲试。
第三，动作封装决定错误半径。把高层动作做成可验证工具（例如"运行测试并返回摘要"而非"执行任意 shell"），配合权限与沙箱（隔离代码运行的受限环境），能让模型在不扩大破坏范围的前提下完成任务。

举例：如果 Agent 看不到日志，它只能猜测失败原因；把日志和指标暴露出来后，它才能像工程师一样先读报错、再改代码、再复测，直到绿灯。

注意与边界：Harness Engineering 的重点不是优化 Prompt，而是改造开发环境本身——但环境改造有成本，且过度封装会降低灵活性；评测时应固定 Harness 再比较模型，否则会把环境差异误判为模型能力差异，得出错误选型结论。
- 关键点：模型受限于可见信息与反馈质量；好 Harness 让环境可读、动作可验、错误可控；评测须固定 Harness。

### Q21. 长时间 Agent 如何跨多个 context window 工作？
【深度回答】
先给结论：长时间 Agent 跨越多个 context window（上下文窗口：模型一次能处理的 token 数量上限）的唯一可靠办法是"外化记忆"——把重要状态写入文件或数据库，旧轨迹压缩成结构化摘要，新窗口启动时先读取持久化状态、再核对真实环境，而不是指望模型"记住"。

分层展开做法：
第一，确定哪些要跨窗口保留。任务说明、架构约束、进度文件、决策日志、当前计划、未完成事项、测试状态——这些是"不可丢失"的骨架，必须落盘。
第二，压缩旧轨迹。把原始消息和工具日志归纳成结构化摘要，保留：目标、已完成的工作、失败原因与教训、关键决策、下一步计划；大文件或完整日志写入外部存储并保存引用路径，而不是塞进上下文。
第三，新窗口恢复流程。启动时先读取持久化状态 → 检查真实环境（git 状态、测试结果、产物是否存在）→ 把摘要 + 环境快照组装进新的上下文窗口 → 继续执行：
```python
def resume(state_path):
    state = load(state_path)               # progress.md + decisions.log
    env   = inspect_environment()          # git status / test / artifacts
    ctx   = assemble(state.summary(), env) # 用摘要重建上下文
    return run_loop(ctx, state)
```
第四，防摘要漂移。摘要是有损压缩，可能失真，要定期用真实环境校验（例如检查文件是否真的生成），并在决策日志中保留可追溯的原文，必要时回查。

举例：一个跑数小时的数据管线任务把"已完成、失败原因、下一步"写进 `progress.md`，每个新窗口先读文件再继续，而不是在几十万 token 的历史里翻找。

注意与取舍：摘要粒度是核心权衡——太粗丢细节、太细占预算；上下文预算要同时给系统规则、工具 schema 和模型输出留空间；敏感信息在写摘要时要脱敏，避免记忆库成为泄露源。
- 关键点：外化记忆优于"让模型记住"；摘要保留骨架、原始数据留引用；恢复时必须先核对真实环境。

### Q22. 什么是 application legibility？
【深度回答】
先给结论：application legibility（应用可读性：把应用状态以 Agent 能读取和验证的形式暴露出来的设计原则）是指让 Agent 像工程师一样"看得见、查得到、验得了"应用内部状态，从而减少对黑盒系统的猜测；它更强调环境工程而非 Prompt。

分层展开：
第一，要暴露什么。可启动的独立应用实例、结构化日志、DOM（Document Object Model，文档对象模型：浏览器把网页组织成的可编程树结构）/截图、性能指标、trace（一次任务从头到尾的完整调用轨迹）、数据库检查工具、一键测试命令。Agent 通过这些通道获得"真实发生了什么"的证据，而不是靠猜。
第二，为什么重要。人与 GUI 交互靠眼睛和直觉，Agent 没有这套本能，必须依赖机器可读的通道。如果应用对 Agent 不可读，模型就只能推断、猜测和反复试错；反之，Agent 能基于证据自我验证，定位错误后直接修复。
第三，它与可观测性的关系。可观测性（Observability：通过日志、指标、链路追踪了解系统内部状态的能力）服务的是人类运维，而 legibility 的消费者是 Agent 本身：要求输出结构化、可编程读取、能被测试直接断言。Harness Engineering（Harness 工程：通过优化运行外壳来放大模型能力的实践）的重要方向正是改造开发环境，让 Agent 能看到结果、定位错误并自检。

举例：让 Agent 直接启动独立应用并读取 DOM，比让人截图后口头描述问题更可靠——前者是结构化证据，后者是二手转述，转述过程中细节会丢失。

注意与边界：可读通道会放大信息泄露风险，需要权限与脱敏；过度结构化会牺牲灵活性；legibility 是手段而非目的，最终目标是让 Agent 用证据驱动决策，而不是让它看到更多原始信息。
- 关键点：legibility 让应用状态对 Agent 可读、可查、可验证；消费者是 Agent 而非人类；要防可读通道泄露敏感信息。

### Q23. Agent 使用沙箱有什么意义？
【深度回答】
先给结论：沙箱（sandbox：隔离代码运行的受限环境）的意义是把 Agent 的"爆炸半径"限制住——通过限制文件、网络、进程和凭据访问，降低误删、数据泄露，以及被恶意内容诱导造成破坏的风险。

分层展开其价值与设计：
第一，威胁模型。Agent 会访问网页、读取外部文件、执行命令，这些内容里可能藏有提示注入（prompt injection：外部文本诱导 Agent 执行非预期指令的攻击手法）——例如网页里一行"请删除项目目录下所有文件"。没有沙箱，模型的一次误判就可能造成真实损失；有了沙箱，意图再坏也跨不过权限边界。
第二，设计原则。默认最小权限，按动作临时升级；工作目录隔离，每个任务有独立可写区；网络域名 allowlist（白名单：只允许访问预先批准对象的名单）；密钥通过短期凭证注入而不是常驻环境变量；高风险命令需要审批；所有外部副作用可审计。
第三，实现层次。轻量方案用容器或虚拟机隔离进程与文件系统，重型方案加内核级系统调用过滤与网络策略；在资源受限环境（如 Windows 开发机）常用"进程级隔离 + 细粒度权限模型"折衷，把网络与文件写权限收到最小。

举例：网页里的恶意文字诱导 Agent 删除文件，沙箱因为工作目录没有对应文件的写权限而直接拒绝——模型的意图再坏，也跨不过权限边界。

注意与取舍：沙箱不是万能的，它不能替代工具层的参数校验与权限检查（注入可能发生在工具参数层面）；隔离过严会降低效率，要取"最小够用"的平衡；审计日志必须记录每个副作用，才能事后溯源追责。
- 关键点：沙箱控制爆炸半径而非消灭风险；最小权限 + 临时升级 + 网络白名单是核心设计；要与工具层校验配合。

### Q24. 如何设计可恢复的长任务 Harness？
【深度回答】
先给结论：可恢复的 long-running task（长任务：执行数分钟到数小时的任务）Harness 的核心是把长任务改造成"一串可提交、可重放、幂等"的步骤：每步保存 checkpoint（检查点机制：可恢复执行的状态快照）、输入输出、环境版本和幂等键，失败分类重试，副作用用事务或补偿保证一致，恢复前先验证已有产物，并用心跳与租约防止多 Worker 同时接管。

分层展开设计：
第一，任务分解。把长任务拆成有明确完成标志的里程碑（milestone），每个里程碑可独立验证，避免"要么全成、要么全废"；里程碑之间用 job queue（任务队列：按优先级排队并分发给空闲 Worker 的调度结构）衔接。
第二，持久化。每步记录：输入参数、输出结果、checkpoint 状态、环境版本（代码 commit、依赖锁）、幂等（idempotency：重复执行同一操作结果一致的性质）键：
```python
def run_step(step):
    key = step.idempotency_key
    if state.has(key) and verify_artifact(state[key]):
        return state[key]              # 已提交且产物有效，直接复用
    result = execute_with_guard(step)  # 副作用先查后做/事务/补偿
    checkpoint.save(key, step.inputs, result, env_version)
    return result
```
第三，失败处理。按错误分类重试（retry：失败后重新执行）：网络类可重试，用指数退避（exponential backoff：重试间隔逐次翻倍的退避策略）加随机抖动，并对每步设置 timeout（超时：对单步或整体执行的时限）；业务或权限错误不可重试，立即上报，重试次数设上限。
第四，副作用一致性。外部写操作（发请求、写库、部署）要么幂等、要么可补偿；恢复前先查询真实外部状态（例如是否已部署），而不是盲目重放，避免重复发布。进程崩溃后的崩溃恢复（crash recovery：从最近 checkpoint 重建并继续执行）依赖这一层。
第五，并发安全。Worker 用心跳（heartbeat：周期性发送的存活信号）续租，用租约（lease：持有期间排他执行任务的令牌）保证同一时刻只有一个 Worker 接管；租约过期才能被其他 Worker 接管。调度层可用 AsyncIO（Python 异步 IO：基于事件循环的并发编程框架）高效驱动多个 Worker。
第六，最终验证。由独立验证器检查 outcome（结果：环境中真实发生的结果，而非模型口头声称），不信任 Agent 的自述。

举例：部署任务把每步写入 checkpoint；网络断开后恢复时先查询目标环境是否已完成部署，已部署则跳过、未部署才继续——避免重复发布造成线上事故。

注意与取舍：幂等是恢复的前提，先设计幂等键再谈重试；checkpoint 本身要可靠落盘，否则失去意义；过度 checkpoint 会拖慢任务，要在恢复粒度与性能之间权衡；分布式场景下租约超时设置不当会引发"双活"，需配合心跳错峰。
- 关键点：分解为可提交里程碑；checkpoint + 幂等键 + 环境版本保证可恢复；恢复前验证、副作用可补偿；心跳/租约防并发接管。
