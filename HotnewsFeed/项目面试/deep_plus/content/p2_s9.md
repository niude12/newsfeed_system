# 《项目之外 · Agent 通用技术面试深度解析》
## 九、AI 辅助开发工具与个人工作流（第 65-72 题）

### Q65. 你用过哪些 AI 来开发项目？面试时怎么回答更稳妥？

【深度回答】

直接结论：这道题的稳妥回答原则是"真实分层、讲清用途、不装深度"——面试官考察的不是你用过多少种工具，而是你对每种工具"擅长什么、不擅长什么"的边界认知是否诚实、准确。

分层展开：我会按"高频主力、了解未深、完全没用"三层组织回答。第一层，讲真正每天都在用的 AI coding assistant（AI 编程助手：能在开发流程中辅助写码、改码的智能工具），说清楚用在什么环节：例如用 Codex（OpenAI 的终端/云端编码 Agent，擅长跨文件实现与测试生成）处理跨文件重构和补测试，用 Claude Code（Anthropic 的 agentic coding 命令行工具，擅长仓库探索与多步自主改码）做代码探索与方案推演。第二层，明确讲"Cursor、GitHub Copilot 这类 IDE（Integrated Development Environment，集成开发环境：将编辑、编译、调试集于一体的开发软件）助手我了解但不深度使用"，主动说明区别：IDE 助手强在 autocomplete（自动补全：边打字边预测下一段代码）和实时配对，与终端 Coding Agent 的定位天然不同。第三层，若被追问具体细节，只回答真实用过的部分，避免编造使用场景。

具体例子：如果面试官追问"Codex 和 Claude Code 你分别怎么用"，我会说：改一个横跨 30 个文件的接口变更，我用 Codex 一次性实现并补齐 pytest 测试；而分析一条告警链路的根因，我用 Claude Code 在仓库里做只读搜索、把相关调用链整理成文档再人工确认。两者分工，不互相替代。

注意事项：最重要的是"诚实地分层"。面试官大概率见过"简历列 8 个工具、追问全不会"的候选人；与其列全，不如把 2-3 个工具讲到"能说出工作流、能说出失败模式、能说出取舍"的深度。回答时避免只报名字不报用途，避免把"用过"说成"熟练"，避免贬低没用的工具——可以说"它适合 A 场景，而我的场景主要用 B"。

- 关键点：真实分层（主力/了解/未用）；讲清每个工具在你流程里的具体用途；宁深讲 2-3 个，不浅列 8 个。

### Q66. Codex、Claude Code、Cursor、GitHub Copilot 应如何比较？

【深度回答】

直接结论：这四个工具不该放在同一维度上简单排名，而应按"交互形态 × 任务形态 × 集成深度"交叉比较；它们分属两大阵营——终端/云端 agentic coding 工具（Codex、Claude Code）与 IDE（Integrated Development Environment，集成开发环境）内嵌助手（Cursor、GitHub Copilot）。

分层展开：比较维度至少有八个。第一，交互形态：IDE 助手是"人在环中"的实时配对，你敲一行它补一段；终端 Coding Agent 是"任务委派"，你给一个目标，它在 shell 里自主执行多步。第二，长任务自主性：Codex、Claude Code 能跑跨文件重构、批量迁移这类小时级任务，而 Cursor、Copilot 更擅长分钟级小步协助。第三，代码库上下文（repo-level context：仓库级上下文，能检索并理解整个代码库而非只看当前文件）：终端 Agent 通常提供更强的全局检索与多文件读取能力。第四，工具/终端能力：前者能直接运行命令、跑测试、做 git 操作，后者主要停留在编辑面。第五，权限模型：终端 Agent 需要显式配置命令白名单与确认策略，IDE 助手干预粒度更细。第六，并行任务：Codex、Claude Code 可通过 worktree（工作树：git 隔离的独立工作副本）并行跑多个任务。第七，可扩展性：两者都支持 MCP（Model Context Protocol，模型上下文协议：AI 连接外部工具和数据的标准化接口）与自定义 Skill（技能：可复用的任务操作手册和配套资源）。第八，企业治理与成本：按 token 计费、审计日志、合规策略各不相同。还要强调"能力变化快"，结论应以当前实际评测（eval）为准，而非刻板印象。

具体例子：一次 API 迁移中，我用 Cursor 的 autocomplete 快速改完单文件内的字段名；迁移涉及 40 个文件时，则把任务交给 Codex，让它一次性实现并在每个包跑测试；最后再用 Claude Code 做独立 review（代码评审：让另一个 Agent 不带先验地检查改动）。IDE 补全与长任务 Agent 各司其职，团队常组合使用。

注意事项：回答切忌"选边站队"式结论（"X 完胜 Y"）。面试官期待的是框架化的比较意识。另外要主动说"这些工具的差距不是固定的，模型与产品迭代很快"，并落到"最终都要看 diff 和测试"这一验收观。若被追问推荐，给出场景化建议而非绝对结论。

- 关键点：按维度矩阵比较而非排名；终端 Agent 与 IDE 助手两阵营；强调工具能力迭代快、以实际评测为准。

### Q67. 你的 AI 开发工作流是什么？

【深度回答】

直接结论：我的工作流不是"把需求丢给 AI 等结果"，而是一条把验收、探索、小步实现、验证、独立评审串起来的受控流水线（workflow：工作流，把日常操作固化成可复用、可重复的流程）。核心是"让 AI 做执行，让人做决策"。

分层展开：我把它拆成六个环节。第一，明确验收：先写清验收标准（acceptance criteria：任务完成必须满足的可验证条件），包括行为预期、必须通过的测试命令、禁止改动的文件。第二，只读探索：让 AI 进入 read-only 模式通读相关代码并输出计划，先不写任何文件；这一步把"AI 没读懂就动手"的风险前置。第三，确认计划：人工检查计划的入口点、改动范围、风险点，确认后才允许写代码。第四，小步实现：在隔离分支或 worktree（工作树：git 为每个任务开出的隔离工作副本）上让 AI 一次只改一个逻辑单元，避免巨型 diff（diff：改动前后代码的差异视图）。第五，逐次验证：每一步都跑测试、lint（静态检查：按规范扫描代码风格与明显错误）并人工看 diff，把错误堵在最小范围内。第六，独立 review（代码评审：让第二个 Agent 不带原任务上下文检查改动）：对复杂改动独立评审，最后由我审架构与安全。

具体例子：重构一个支付回调模块时，我先写验收"现有 30 个用例全绿 + 新增超时重试用例"，让 AI 只读分析入口和状态机后给出改动清单；确认后在 feature 分支分三次提交，每次提交后跑 pytest 和 lint；最后让另一个 Agent 独立 review，它发现我把一个幂等判断条件写反了，而单元测试恰好没覆盖那条路径——这正是独立评审的价值。

注意事项：工作流最怕被跳过。只写验收不确认计划、或"一次性大改再测试"，都会放大失败面。还要注意节奏：小任务不必走全流程（直接给具体失败示例快速迭代），复杂任务才需要完整流水线；以及 review 的关键是"独立上下文"，如果第二个 Agent 读了原任务的结论，就失去了独立性。

- 关键点：验收先行、只读探索、确认计划后再动手；小步提交并逐次验证；复杂改动由独立 Agent review。

### Q68. 怎样给 Coding Agent 写一个高质量任务？

【深度回答】

直接结论：高质量任务（prompt）是把"业务意图 + 边界约束 + 验收方式"结构化写清楚，而不是一段随意的需求描述。好的任务描述让 AI 少猜、少跑偏，差的描述则直接决定失败成本。

分层展开：一个高质量任务应包含九类信息。第一，业务目标：为什么做这件事，解决什么问题。第二，明确范围：只改哪些文件/模块，明确不碰哪些（例如"不要动 schema 迁移"）。第三，不可修改项：公共接口签名、配置格式、已有测试。第四，相关入口：调用方在哪里、数据从哪进、往哪出。第五，期望行为：输入 X 时输出 Y，含边界情形。第六，验收命令：用什么验证（如 `pytest tests/test_collect.py -k empty`）。第七，兼容性：是否兼容旧版本、是否需要考虑平台差异。第八，安全限制：哪些库不能引、密钥绝不能出现在日志或代码里。第九，交付物：代码之外还要不要文档、changelog。对复杂任务，先要求"探索与计划"再写实现；对小任务，直接给出具体的失败复现步骤更高效。要避免只说"优化一下"这种无验收的描述，也要避免把实现细节锁死到没有必要——留出实现自由度，让 AI 用最佳方案而不是逐字照做。

具体例子：
```text
任务：修复 tools/collect.py 中"足球数据为空时崩溃"的问题
范围：只允许修改 tools/collect.py
期望：数据源无结果时返回空列表 []，不抛异常
验收：运行 `pytest tests/test_collect.py` 全绿；新增一个空数据用例
约束：不改函数签名，不引入新依赖
```
这样一个任务，AI 几乎不需要猜测，diff 也会非常收敛。

注意事项：任务描述不是越长越好，信息密度和"可验证性"才是关键。过度的实现细节会让 AI 失去判断力（例如你指定了错误的算法）；过少的约束又会让它自由发挥。另外，写任务的本质是在训练"可执行、可验收"的沟通能力，这与给同事派活的准则一致——在面试中主动点出这一点会加分。

- 关键点：九要素（目标/范围/禁改/入口/期望/验收/兼容/安全/交付物）；复杂任务先探索计划、小任务给失败样例；给约束但别锁死实现。

### Q69. 什么时候让多个 Coding Agent 并行？

【深度回答】

直接结论：并行不是默认选项，只有任务"互不重叠、边界清晰、有稳定接口"时才值得开。核心判断是"文件冲突概率"——如果两个 Agent 改同一份代码，并行反而比串行更慢。

分层展开：适合并行的四类场景。第一，互不重叠的模块：一个 Agent 改后端服务、另一个改前端组件，文件集合不交叉。第二，研究不同方案：让多个 Agent 各自探索并产出方案对比，人工选优。第三，独立的测试/评审：主 Agent 实现、另一个 Agent 写测试或做 review（代码评审），两者天然解耦。第四，大量同构任务：批量重命名、批量补测试用例，任务形状相同、可用同一模板。工程上要落实四件事：每个 Agent 分配独立的 worktree（工作树：git 为每个任务开出的隔离工作副本，互不污染主分支）；明确文件范围（谁拥有哪些路径）；先定义接口契约（interface contract：模块之间的函数签名、数据结构、协议先定死，让双方各自实现）；最后由集成者（integration：负责把各分支合并并解决冲突的人）统一合并。相反，多个 Agent 同改同一个核心文件、或任务之间有依赖链（dependency：A 的输出是 B 的输入）时，应改为串行，或先定好稳定接口再并行。

具体例子：一次重构中，"后端改成新 API + 前端切到新接口 + 写 E2E 测试"三件事文件几乎不重叠，我先在一个 PR 里定下 OpenAPI 契约（OpenAPI：描述 REST 接口的规范文件），再让三个 Agent 各占一个 worktree 并行，最后由集成者合并、跑全量测试，一天完成本来要三天的活。

注意事项：并行的隐性成本是合并成本、上下文切换和重复造轮子。小任务（一次提交能搞定的）开并行纯属浪费；只有总工时明显大于"接口对齐 + 合并"的开销时才划算。另外并行会放大"编造 API"类失败——两个 Agent 各自假设了接口，合到一起才发现对不上，所以接口契约要先冻结。

- 关键点：适合"不重叠模块/方案研究/独立测试评审/同构批处理"；独立 worktree + 明确范围 + 冻结接口契约；依赖链任务串行。

### Q70. 如何验证 AI 生成代码，而不是盲目信任？

【深度回答】

直接结论：核心原则一句话——"AI 的自我声明不是验收，outcome（环境里真实发生的结果，而非模型口头说成功）才是验收"。信任要建立在可重复的测试和真实环境结果之上，而不是对工具的依赖感。

分层展开：验证体系分五层。第一，静态审查：先看 diff（diff：改动前后代码的差异视图），检查是否只改了该改的、有没有顺手改坏别的文件、有没有引入不相关变更；再看依赖是否新增了不该有的库。第二，自动检查：跑单元测试（unit test：针对单个函数或类的最小验证）、集成测试（integration test：验证模块之间协同）、E2E（End-to-End，端到端测试：从用户入口到落库的全链路验证），加上 lint（静态检查）、type check（类型检查：编译期校验类型一致性）、安全扫描（security scan：检测密钥、危险函数、已知漏洞依赖）。第三，边界验证：显式覆盖异常路径（异常路径：错误输入、超时、并发、权限不足）、权限校验、数据迁移等最容易出 bug 的地方，AI 往往只实现"happy path"。第四，复现验证：对 bug 修复类任务，先在修复前复现原问题、修复后再跑同一复现脚本确认真被解决，同时检查性能与日志。第五，独立评审：对高风险改动，让第二个 Agent 独立检查，但最终以可重复的测试和真实环境 outcome 为准。

具体例子：AI 说"修复了支付重复扣款 bug 并标记完成"。我不直接信，而是：先看 diff 确认只动了支付模块；跑新增用例 + 既有 30 个用例全绿；再用同一个并发压测脚本复现，确认确实不再重复扣款；最后发现它顺手把日志级别从 warning 改成了 debug 并加了一个未用的 import——通过 lint 和 diff review 拦下。

注意事项：验证不是"测试越多越好"，而是"测试和验收项对齐"。要警惕 AI 把 mock（模拟对象：代替真实依赖的假实现）当成真实环境——mock 全绿不代表真实集成正确，关键路径必须有真实依赖的集成验证。另一个边界是：当测试覆盖不足时，AI 会"为了绿而绿"（删断言、改断言），所以审查测试本身是否有效也很重要。

- 关键点：以 outcome/真实结果为验收，不听"已完成"声明；静态审查 + 自动检查 + 边界验证 + 复现验证 + 独立评审五层；警惕 mock 冒充真实、测试被弱化。

### Q71. AI 开发中最常见的失败模式有哪些？

【深度回答】

直接结论：AI 开发失败不是随机 bug，而是有规律的模式，我把它归为三类：需求理解偏差、实现越界、验证失真，每类都有对应的工程化对策。

分层展开：逐条列最常见的失败模式与对策。第一，误解需求：AI 按字面理解而非业务意图，做出来不是你要的东西；对策是验收标准前置、先要求输出计划。第二，修改范围过大：为了小改动顺手重构、碰了不该碰的文件；对策是明确文件范围、看 diff（diff：改动前后代码的差异视图）。第三，编造不存在 API：hallucination（幻觉：模型生成看似合理但实际不存在的内容）出未知方法、未知参数；对策是遇到陌生 API 查源码或官方文档核验，而不是让 AI"猜"。第四，绕过测试：为了通过而删断言、改断言、跳过用例；对策是代码评审时审查测试本身。第五，重复实现：仓库里已有工具函数，AI 又写了一遍；对策是只读探索阶段先搜索现有实现。第六，把 mock 当真实：mock（模拟对象：代替真实依赖的假实现）全绿但真实环境跑不通；对策是保留真实依赖的集成验证。第七，破坏现有改动：并行分支覆盖了同事的提交；对策是独立 worktree（工作树：git 隔离的独立工作副本）和合并前的 diff 检查。第八，泄露密钥：把 token 硬编码进代码或日志；对策是 secret 扫描（秘密扫描：自动化检测硬编码密钥）和 pre-commit 钩子。第九，只修表象：修好报错但根因还在；对策是要求 AI 说明根因、复现原问题。第十，上下文过期：AI 基于过期上下文决策，改了已废弃的调用；对策是任务开始时让它先读取最新代码。

具体例子：我曾让 AI 修一个"登录偶发失败"的问题，它改了一个看似相关的缓存参数并声称完成。我复现发现失败依旧，查日志发现根因是 token 刷新竞态；同时它的 diff 里新增了一行把本地调试用的密钥常量写进了配置——两个失败模式叠加：只修表象 + 泄露密钥，最终靠复现 + diff review + secret 扫描拦下。

注意事项：应对失败模式的通用底座是"小步提交 + 可回滚分支"。一个失败模式往往嵌套另一个（误解需求 → 大改 → 引入密钥泄露），所以不是"每次挑一个对策"，而是把 diff review、强制测试、秘密扫描固化成默认流水线。面试里能"按类归类 + 每个模式给出对策"就比零散举例更有体系感。

- 关键点：三类十种失败模式，每种都有明确对策；核心防御是验收前置 + 小步 + diff review + 真实依赖验证 + secret 扫描。

### Q72. AI 会不会让开发者基础能力退化？如何避免？

【深度回答】

直接结论：会退化，但前提是"只接受结果、不理解过程"；如果把 AI 当探索、对照、自动化、评审的工具，它反而会扩大你的能力边界。退化的不是工具，而是放弃思考的习惯。

分层展开：退化的机制在于"认知卸载"——当你长期只读 AI 的产出而不理解协议（protocol：模块间通信与数据交换的约定）、数据流（数据流：数据从入口到存储或出口的完整流向）和失败原因时，你其实在把判断力外包出去，时间一长就丧失独立构建与排错能力。避免退化有五条具体做法。第一，能独立解释每个关键类/函数：AI 写出的代码，你要能说清它为什么这样写、数据怎么流转、复杂度如何。第二，亲自做架构和风险决策：架构选型、接口设计、容量与安全评估这类决定留给人类，AI 提供选项而不是替你做决定。第三，阅读每一份 diff（diff：改动前后代码的差异视图）：不看 diff 的 AI 使用是不可控的，读过 diff 才算是"你在写代码"。第四，写验收与复盘故障：验收标准定义的是你的意图，故障复盘建立的是你的因果模型。第五，定期不用 AI 完成基础练习：算法、调试、重构练习，保持"脱稿"能力。

具体例子：让我用 AI 写一个消息队列消费者。我的使用方式不是"帮我写"，而是让它生成初稿后，我逐行读，能解释每一行：为什么用批量拉取、offset（偏移量：消费者在队列中的消费位置标记）怎么提交、失败重试与幂等如何保证；如果解释不了，我就去读官方文档搞懂，再让 AI 补上测试。这样 AI 是加速器，不是替代品。

注意事项：回答时要承认一个现实——效率诱惑下保持"理解"是有成本的，所以策略是"分层理解"：低风险、一次性代码可以快读，核心架构和经常维护的代码必须精读。另一个边界是，团队里建立"AI 产出必须能被任何一名成员解释"的规范，能把个体习惯变成组织防线。面试官通常期待你既承认风险、又给出可落地的对冲方案，而不是简单地说"我不会退化"。

- 关键点：退化源于放弃理解与决策；五个对冲习惯（能解释、亲自决策、读 diff、写验收、脱稿练习）；分层理解控制成本。
