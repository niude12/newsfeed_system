# 《项目之外 · Agent 通用技术面试深度解析》
## 十、主流框架、架构选型与趋势判断（第 73-80 题）

### Q73. LangChain、LangGraph、AutoGen、CrewAI 的定位有什么不同？
【深度回答】
直接结论：这四个库虽然都叫 Agent framework（Agent 框架：构建 Agent 应用的开发框架），但抽象层次与核心原语完全不同——LangChain 是"组件集成库"，LangGraph 是"图运行时"，AutoGen 是"对话协作框架"，CrewAI 是"角色团队框架"；选型应看任务结构而非流行度。

分层展开定位对比：

| 框架 | 定位 | 核心抽象 | 最擅长场景 |
|---|---|---|---|
| LangChain（连接 LLM 与工具链的编排库） | 组件库 | Model / Retriever / Tool 统一接口 | 模型调用、提示模板、RAG 组件集成 |
| LangGraph（有状态图编排的 Agent 框架） | 图运行时 | State（状态）/ Node（节点）/ Edge（边） | 多分支、循环、暂停恢复、持久化长任务 |
| AutoGen（微软的多 Agent 对话框架） | 对话协作 | ConversableAgent（可对话智能体）群聊 | 多角色轮流发言、谈判、迭代生成 |
| CrewAI（以"角色团队"组织的多 Agent 框架） | 角色团队 | Role（角色）/ Goal（目标）/ Backstory（背景） | 贴近业务组织结构的任务分工协作 |

- LangChain 解决"怎么把模型接到数据和工具上"，本身不规定运行拓扑，流程固定时反而显得重。
- LangGraph 把执行逻辑显式建模成图，核心价值在于 checkpoint（检查点：保存图中间状态以便恢复）、interrupt（中断：暂停执行等待人工或外部输入）、并行与 durable execution（持久化执行：崩溃后从最近检查点恢复而非从头重跑）。
- AutoGen 以"对话"为协作原语，多个 Agent 通过群聊轮流发言推进任务，天然支持 HITL（Human-in-the-Loop，人工介入：关键步骤暂停等待人工确认）。
- CrewAI 以角色分工为组织方式，每个 Agent 有明确身份与目标，API 对人类友好、上手快。

一个具体例子：要做"热榜采集→聚类→评分"这种固定依赖链，用普通 Python 顺序调用更透明；要做"自动生成简报→人工审批→审批后继续发布"这种可暂停、可恢复的流程，用 LangGraph 的图状态最合适；要让"检索、写作、审校"三个角色来回讨论，AutoGen 或 CrewAI 更顺手。

注意事项与边界：切忌 golden hammer（银弹陷阱：对任何问题都套同一框架）。框架锁定（framework lock-in，绑定单一框架后难以迁移）成本高，且框架层抽象掉底层细节，出错时调试链路更长。应坚持"简单流程用普通代码，复杂图用 LangGraph，对话协作看 AutoGen/CrewAI"，并且可以混合使用——例如用 LangGraph 做编排、用 MCP（Model Context Protocol，模型上下文协议：Agent 连接工具与数据源的标准协议）做工具接入，两者并不冲突。

- 关键点：四个框架抽象层次不同（组件库/图运行时/对话协作/角色团队）；选型看"任务结构+可恢复性需求"；避免银弹陷阱与框架锁定。

### Q74. OpenAI Agents SDK 常见核心概念有哪些？
【深度回答】
直接结论：OpenAI Agents SDK（OpenAI 官方推出的轻量 Agent 开发框架）的核心概念可分为三类：组成单元（Agent、instructions、tools）、协作机制（handoffs）、工程保障（guardrails、sessions/memory、tracing、evals）。

分层展开核心概念：
- Agent（智能体：由指令、工具和护栏组成的独立执行单元）：一个 Agent 定义"你是谁、能做什么、怎么做"，是 SDK 最基本的执行单位。
- instructions（指令集：定义 Agent 行为与边界的系统提示）：相当于 system prompt，写清角色、风格、安全边界与任务策略。
- tools（工具：Agent 可调用的函数）：可以是普通函数、远程 API，也可以是另一个 Agent，即 agent-as-tool（把 Agent 封装成工具供其他 Agent 调用，实现递归组合）。
- handoffs（交接：把对话控制权从一个 Agent 转给另一个 Agent 的机制）：这是 SDK 最核心的协作原语，支持 triage routing（分流路由：入口 Agent 先判断任务类型，再转交给专业 Agent）。
- guardrails（护栏：在模型输入/输出上执行的校验拦截逻辑）：可在调用模型前拦截不安全输入，也可在输出后校验格式，失败即中断——不能只靠 Prompt。
- sessions/memory（会话与记忆：跨对话轮次持久化消息上下文）：让 Agent 在多次请求之间保持状态。
- tracing（追踪：记录一次运行的完整事件链路、token 与成本）：用于调试与回放。
- evals（评测：用代码对 Agent 行为做自动化评估）：跑回归，防止功能退化。

一个具体例子：客服场景中，入口分流 Agent 先用 guardrails 拦截越权请求，判断是"退款"还是"改地址"后，通过 handoff 把对话转交给对应的专业 Agent；全程由 tracing 记录每个环节的工具调用与 token 消耗，事后用 evals 回归"是否总能转交给正确 Agent"。

注意事项与边界：SDK 只做"Agent 运行层"，业务状态（订单号、审批流）、权限、数据一致性、验收标准仍需自行设计；它默认依赖 OpenAI 模型生态，若要多供应商或私有化部署，需评估替换成本。适合"用 OpenAI 模型快速搭建生产 Agent"的场景，但不要把它自带的 tracing 当成完整的可观测性体系。

- 关键点：核心四件套是 Agent/tools/handoffs/guardrails；常见模式是 triage routing + agent-as-tool；业务状态与验收仍需自建。

### Q75. AutoGen 的 RoundRobin、Selector、Swarm、GraphFlow 如何选择？
【深度回答】
直接结论：四种协作策略的本质差异在"谁来决定下一个发言者"以及"流程是否预先确定"——确定性从高到低大致是 GraphFlow、RoundRobin、Selector、Swarm；选型看依赖复杂度与是否需要动态决策。

分层展开四种策略：
- RoundRobin（轮流发言：按固定顺序让每个 Agent 依次发言）：流程完全确定、实现最简单，适合背景相近的 Agent 做固定评审或头脑风暴；但无法根据内容调整顺序，效率偏低。
- Selector（选择器：用模型或函数动态决定下一个发言者）：每个 Agent 发言后由"选择函数/模型"评估谁最该接话，比轮流灵活；适合参与者能力或相关性随任务变化的场景，但会引入一次额外 LLM 调用与误差。
- Swarm（群体协作：由当前 Agent 通过 handoff 局部决定转交给谁）：决策去中心化，当前发言者直接把控制权交给下一个专家，链路灵活、接近真实团队协作；但共享上下文易膨胀、终止条件与责任归属更难控制。
- GraphFlow（图流程：用有向图显式表达顺序、并行、条件分支与循环）：把协作流程画成图，确定性与可恢复性最高，支持条件路由与并行；建模成本也最高。

一个具体例子：三个 Agent 固定轮流评审代码用 RoundRobin；"先分析问题、再动态决定找财务还是法律专家"用 Selector；专家之间链式转交（财务→审计→风控）用 Swarm；"检索→并行分析→汇总裁决→人工复核"这种有依赖、有并行、需中断恢复的流程用 GraphFlow。

注意事项与边界：无论哪种策略，都必须设置 termination condition（终止条件，如达成一致或达到轮数上限）、max_turns（最大发言轮数）和状态保存，否则群聊容易空转或死循环。Swarm 的去中心化是一把双刃剑：生产系统常采用混合模式——大任务由中心编排（GraphFlow），局部小团队内部用 Swarm，兼顾可控性与灵活性。

- 关键点：确定性排序 GraphFlow>RoundRobin>Selector>Swarm；必须有终止条件与轮数上限；生产常用"中心编排+局部 Swarm"混合模式。

### Q76. Agentic Workflow 的五种经典模式是什么？
【深度回答】
直接结论：Anthropic 在《Building Effective Agents》中把 Agentic Workflow（Agent 工作流：把任务拆分为模型参与的多步流程）归纳为五种经典模式——Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer；它们之上才是完全自主的 Autonomous Agent（自主 Agent：自行决定目标与路径、不预设步骤）。

分层展开五种模式及适用条件：
- Prompt Chaining（提示链：把任务拆成顺序步骤，上一步输出作为下一步输入）：适合固定分解、每步可校验的任务，如"先抽取事实，再写摘要，再校对"。优点是每步可控可观测；缺点是延迟叠加、误差逐级传播。
- Routing（路由：根据输入特征分类，选择不同处理路径）：适合类别明确、各路径差异大的任务，如按语言/意图/渠道分发；用小模型分类比大模型直接处理更便宜。
- Parallelization（并行化：同时执行多个独立子任务，再聚合结果）：适合子任务无依赖的场景，如多路独立检索、多专家并行评审；能显著降延迟，但要处理聚合冲突。
- Orchestrator-Workers（编排者-执行者：中心 Agent 动态拆解、分派并汇总）：适合子任务无法预先枚举、需动态规划的任务，中心节点统管全局预算与权限；代价是中心成为瓶颈。
- Evaluator-Optimizer（评估者-优化者：一个 Agent 生成，另一个 Agent 评估并反馈，循环改进）：适合有明确质量标准且可迭代度量的任务，如写作润色、代码优化；需设置迭代上限防止无限循环。

一个具体例子：文章先写后审是 Prompt Chaining；客服按"退款/改地址/查询"分发给不同专业 Agent 是 Routing；同时让三个模型分别评审代码的正确性、性能和风格再汇总是 Parallelization；"自动生成行业简报"由主编 Agent 动态拆成检索、图表、排版三个子任务再汇总是 Orchestrator-Workers；先写初稿再由评估 Agent 打分返回修改是 Evaluator-Optimizer。

注意事项与边界：这五种模式不是"越复杂越好"——应从最简单的 Chaining 起步，只有评测证明更复杂模式带来收益才升级，因为越复杂延迟、成本、不可预测性越高。工作流（Workflow，路径由代码/图预先确定）与自主 Agent（路径由模型实时决定）的关键区别，正是"路径是否预先确定"。

- 关键点：五种模式各有明确适用条件（固定分解/类别明确/可并行/子任务未知/质量可迭代）；从最简单模式起步；区别于完全自主的 Autonomous Agent。

### Q77. 什么是 Computer Use Agent？与 API Tool Agent 有什么区别？
【深度回答】
直接结论：两者的本质区别是"操作通道"不同——API Tool Agent（API 工具 Agent：通过调用结构化接口完成任务）操作的是数据和函数，Computer Use Agent（计算机使用 Agent：通过截图/DOM 和鼠标键盘操作图形界面完成任务）操作的是屏幕和界面；能用 API 时应优先用 API。

分层展开对比：

| 对比维度 | API Tool Agent | Computer Use Agent |
|---|---|---|
| 交互对象 | 结构化 API/函数 | 屏幕像素 + 鼠标键盘 |
| 输入 | JSON 参数 | 截图、DOM（Document Object Model，文档对象模型）、坐标 |
| 速度与确定性 | 快、结果确定 | 慢、受 UI 变动影响大 |
| 可测试性 | 高，可做 schema 校验与 mock | 低，需视觉状态确认 |
| 权限粒度 | 参数级，清晰 | 整机操作，粒度粗 |
| 主要风险 | 注入面小 | 提示词注入、误操作、隐私泄露 |

API Tool Agent 依赖"能力可被接口化"：参数结构化、返回可验证、权限可控，因此可测试性高、可回滚、成本低。Computer Use Agent 则模拟人类操作图形界面：感知层用截图或 DOM 获取界面状态，行动层输出鼠标点击/键盘输入，再截图确认结果，形成"观察-行动-验证"闭环。它适合没有 API 的遗留系统、跨应用集成或纯 GUI 场景。

一个具体例子：订票场景中，航司提供 API 就调 API——参数清晰、返回确定、权限精确；只有航司仅有网页、没有接口时，才让 Computer Use Agent 打开浏览器，按座位号点击、输入乘机人信息，并用截图确认"出票成功"页面。

注意事项与边界：Computer Use 必须做动作后验证（确认界面真的发生变化）、敏感操作审批（付款/删除前暂停）、隔离浏览器沙箱（sandbox：限制文件与网络访问的隔离环境）与提示词注入防护（网页内容可能诱导 Agent 执行危险操作）。接口是"优先解"，计算机使用是"兜底解"；若界面频繁改版，Computer Use 方案的维护成本会很高。

- 关键点：区别在操作通道（API vs 图形界面）；API 优先、Computer Use 兜底；Computer Use 必须配视觉验证、审批与沙箱。

### Q78. 什么是 Model Routing？
【深度回答】
直接结论：Model Routing（模型路由：根据任务特征动态选择不同 LLM 处理）就是"让合适难度的任务找合适的模型"，核心目标是在降延迟、降成本的同时不牺牲质量——通过规则或分类器把简单任务导向便宜小模型、复杂任务导向强模型。

分层展开实现方式：
- 规则路由：按任务类型、模态（文本/图像）、长度、关键词等硬规则直接选模型，最简单也最可解释。
- 分类器路由：用小模型或 Embedding（文本向量化：把文本映射成可比较的向量）相似度对任务意图/难度分类，再映射到模型池；比硬规则更灵活。
- 动态升级/回退：先派给便宜模型，若其置信度低、输出格式不合格或工具调用失败，再升级到强模型处理，即 escalation/fallback（升级/回退机制）。

路由决策要综合考虑五类维度：难度、模态、延迟预算、成本预算、隐私合规（敏感数据只能进私有化模型）、工具能力（某些模型不支持结构化输出或视觉输入）。

一个具体例子：客服场景中，简单 FAQ（Frequently Asked Questions，常见问题）分类直接走便宜小模型（延迟低、成本低）；小模型对"复杂多步退款"判断置信度低于阈值时，自动把请求升级给强模型；同时把高频问答命中缓存，连模型调用都省掉。

注意事项与边界：路由本身会引入"误判"风险——把复杂任务判成简单任务导致失败，因此必须监控每条请求的置信度、质量与失败率，定期用 eval（评测：对模型行为做量化评估）校准路由规则；路由决策记录还应包含 prompt/model 版本与缓存命中情况，否则无法复盘"为什么这条走了贵模型"。不能只为了省成本牺牲质量，路由优化必须用质量指标做护栏。

- 关键点：目标是在成本/延迟与质量之间取最优；实现分规则、分类器、动态升级三档；必须有置信度监控与质量护栏。

### Q79. 你怎么看 2026 年 Agent 开发的重点变化？
【深度回答】
直接结论：2026 年 Agent 开发的重心已从"模型能不能调用工具"这种单轮能力，转向"能不能长时间稳定地工作"这种工程能力——面试和高价值系统更关注状态恢复、上下文控制、权限限制、评测与追踪。

分层展开重点转移方向：
- 从"调工具"到"长时间稳定运行"：焦点从 demo（演示）转向 durable execution（持久化执行：崩溃或暂停后从检查点恢复）、checkpoint（检查点：保存可恢复的执行快照）、长任务的进度与失败恢复——能否在 50 轮工具调用后仍不偏离目标，比能否调用工具更关键。
- 从 Prompt 到 Context Engineering（上下文工程：决定"给模型看哪些信息"的系统性方法）：长窗口不是免死金牌，如何压缩历史、外化记忆、按需检索，成为 Agent 能否持续正确的前提。
- 从"裸模型"到 Harness（外壳：让模型能循环、用工具、受约束运行的环境）与 Skills（技能：可复用的任务操作手册）：模型只是引擎，Harness 决定能力上限；Skills 把团队经验沉淀为可复用资产，避免每次重复解释流程。
- 从"能用"到"可控可测"：Evals（评测）与 Observability（可观测性：对系统运行状态的可视化与追踪）成为标配——上线必须能回答"效果如何、出错在哪、花了多少钱、是否越权"。
- 协议层标准化：MCP（Model Context Protocol，模型上下文协议：Agent 连接工具与数据源的标准协议）解决工具接入，A2A（Agent-to-Agent：Agent 间协作协议）解决跨 Agent 协作，两者互补，避免生态碎片化。

一个具体例子：过去面试问"你让 Agent 调了哪些 API"，现在更常追问"长任务跑到第 30 步崩溃了怎么恢复""你怎么证明它修好了而不是说修好了""给它的工具权限怎么收敛"——这些本质都是工程问题，而非模型能力问题。

注意事项与边界：趋势判断不能只追热点——reactive（响应式：被动等待任务）与 proactive（主动式：自主发起任务）的度要按场景把控，不是越自主越好。框架和模型更新快，但底层工程原则（状态可恢复、上下文可控、权限最小化、结果可评测）长期稳定，回答时应强调原则而非具体版本号。

- 关键点：重心转向长期稳定运行与工程化（状态/上下文/权限/评测/追踪）；协议标准化（MCP+A2A）降低碎片化；底层工程原则比具体框架稳定。

### Q80. 请设计一个生产级 Agent 平台的分层架构。
【深度回答】
直接结论：生产级 Agent 平台应自顶向下分成"入口层→编排层→模型网关→工具层→记忆与 RAG 层→运行时→可观测与评测层"七层，每层职责单一、边界清晰，通过稳定接口互相协作。

分层展开各层职责：
- 入口层（API Gateway，API 网关）：负责用户认证、鉴权、限流、租户隔离，是唯一对外暴露面。
- 编排层（Orchestration）：跑 Agent Loop（Agent 循环：感知-决策-执行的迭代）、Graph（状态图）、任务状态机；负责暂停/恢复、HITL（Human-in-the-Loop，人工介入：高风险节点暂停等待人工确认）、超时与重试策略。
- 模型网关（Model Gateway）：模型路由、多供应商切换、缓存、限流、密钥管理；统一 prompt/model 版本。
- 工具层（Tool Layer）：通过 MCP（Model Context Protocol，模型上下文协议：Agent 连接工具与数据源的标准协议）统一接入工具；负责工具注册、描述审核、参数校验与权限映射。
- 记忆与 RAG 层（Memory & RAG，记忆与检索增强生成层）：短期会话记忆、长期用户偏好、向量库检索；负责写入质量门槛与权限隔离。
- 运行时（Runtime）：沙箱（sandbox：限制文件/网络/进程的隔离执行环境）、任务队列、Worker（工作进程）池、故障恢复，让 Agent 在受控环境里执行动作。
- 可观测与评测层（Observability & Evals）：trace（链路追踪）记录、指标、成本计量、评测集回归、Guardrails（护栏：对越权/注入等风险做拦截）。

一个具体例子：用户请求从入口层鉴权后进入编排层，编排层把任务建模成图并派给 Worker；模型网关按难度路由到合适模型，工具层经 MCP 调用数据库；记忆层提供该用户长期偏好，运行时沙箱执行文件操作；全程 trace 可上钻查证，评测平台每天跑回归集防退步，Guardrails 在工具调用前拦截越权动作。

注意事项与边界：分层的关键是"职责不越界"——编排层不直接连数据库、工具层不持有用户密钥、模型网关不做业务校验。每层都要可独立扩缩与替换；安全边界应跨层叠加（输入校验、工具权限、沙箱、人工审批互为纵深防御）。此外要预留配置驱动（declarative config，声明式配置）与扩展点，避免平台僵化，并警惕过度设计——先保证每层有清晰的失败模式与恢复路径，再谈高可用。

- 关键点：七层架构（入口/编排/模型网关/工具/记忆RAG/运行时/可观测评测）；职责单一、跨层安全叠加；先保证可诊断可恢复，再追求高可用。
