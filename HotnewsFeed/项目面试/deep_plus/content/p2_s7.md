# 《项目之外 · Agent 通用技术面试深度解析》
## 七、多 Agent、协议与协作模式（第 49-56 题）

### Q49. 多 Agent 常见协作模式有哪些？
【深度回答】
直接结论：多 Agent（Multi-Agent，多智能体：多个 Agent 协作完成任务）的常见协作模式可归纳为五大类——中心编排、路由、并行聚合、评审迭代、平级交接，没有哪一种"一定最好"，选型取决于任务能否预先拆分、是否需要中心控制、能否并行。

分层展开原理/工程实践：
1. Orchestrator-Workers（中心编排-工作者：由一个 Orchestrator 统一拆解、派发和汇总）。主 Agent 充当 orchestrator（编排者：统一调度其他 Agent 的协调节点），把任务分解成子任务派给 Worker（工作者：执行具体子任务的 Agent），再聚合结果。优点是全局可观测、预算与权限集中可控；缺点是中心是瓶颈和单点故障。
2. Routing（路由：按意图把任务分给合适 Agent）。一个 triage（分流：先按意图把请求分类的入口）Agent 根据请求类型转发给专家，例如客服入口按"退款/技术/物流"分类。适合类别边界清晰的场景，路由规则既可以是规则表也可以是模型判断。
3. Parallelization（并行化：多个 Worker 同时处理互不依赖的子任务）。由 fan-out（扇出：把一个任务拆成多个并行子任务）分发，再由 join（汇聚：等待所有子结果并合并）节点聚合。适合"同时查多个数据源"这类可并行任务，能显著降低端到端延迟。
4. Evaluator-Optimizer（评审-优化：一个 Agent 生成、一个 Agent 评审并反馈迭代）。常用于写代码、写文章等质量可迭代度量的任务，循环直到通过评审或达到次数上限。
5. Swarm / handoff（群体/交接：专家之间通过 handoff 直接转交控制权）。去中心化、路径动态演化，但终止条件与责任归属更难。

具体例子：一个"日报生成"系统用 Orchestrator-Workers 模式——Orchestrator 把"爬新闻、查数据库指标、写报告"分别派给三个 Worker，最后汇总成一份日报；如果某类请求边界清晰（如"查天气"），则用 Routing 直接转发给天气专家。

注意事项与取舍：可预先拆分、需要中心控制选 Orchestrator；类别明确选 Routing；任务可并行选 Parallelization；质量可迭代度量选 Evaluator-Optimizer；只有需要最大灵活性才考虑 Swarm。生产系统常混合使用：中心控制大任务，局部团队内部 handoff。所有模式都必须配套终止条件、超时和全局预算。
- 关键点：五大模式分别对应"可拆分性、类别明确、可并行、可迭代、高灵活"五种诉求；中心编排便于控制但易成瓶颈；生产常用混合模式。

### Q50. 什么时候多 Agent 优于单 Agent？
【深度回答】
直接结论：当子任务需要不同的工具/权限/模型/上下文、任务可并行、或需要独立审查时，多 Agent 才有真实收益；如果只是把同一个 Prompt（指令：给模型的本次任务描述）拆成多个"角色"，通常只会增加延迟、token 和错误传播。

分层展开原理/工程实践：
判断是否值得拆，看四个信号：
1. 工具与权限隔离：子任务需要互斥或最小化的权限集。例如财务 Agent 只能调用支付工具，法律 Agent 只能读合同库；若塞进单 Agent，权限面过大，一次提示词注入可能波及全部工具。
2. 上下文隔离：子任务需要不同的知识库或上下文。让一个 Agent 同时持有财务与法律上下文，会诱发 context pollution（上下文污染：无关或有害信息进入推理上下文、干扰后续决策）。
3. 并行需求：多个互不依赖的子任务串行执行太慢，拆开后并行再由汇聚节点合并，收益直观。
4. 独立审查：生成者与评审者分离，能避免"自己改自己觉得没问题"的自我确认偏差。

工程上的正确姿势是"先单后多"：先尝试单 Agent + 清晰工具集（tools：Agent 可调用的外部函数），跑通后用 eval（评测：用固定指标集衡量系统质量）证明"工具过多、上下文冲突、专业分工确有收益"，再决定拆分。若评测显示提升微弱，立即回退。

具体例子：单 Agent 手里有 5 个边界清晰的工具时没必要拆；但如果系统同时涉及"客户退款"和"合同审核"，两者权限域和数据域完全不同，拆成财务专家 Agent 和法律专家 Agent 才有意义——财务 Agent 永远不会接触合同原文。

注意事项与取舍：多 Agent 的隐性成本包括 coordination overhead（协调开销：Agent 间通信、调度、上下文复制带来的额外资源消耗）、错误传播链变长、调试难度上升。收益必须是可评测的端到端提升，而不是架构上"看起来很高级"。
- 关键点：多 Agent 的价值来自权限/上下文隔离、并行和独立审查，而非角色扮演；先单后多，用 eval 数据决定是否拆分。

### Q51. Orchestrator-Workers 与 Swarm 有什么区别？
【深度回答】
直接结论：两者是两种相反的控制模型——Orchestrator-Workers（中心编排-工作者：由中心节点统一拆解、分派和汇总）是"中心化调度"，Swarm（群体：去中心化平级协作）是"去中心化接力"。

分层展开原理/工程实践：
Orchestrator-Workers 由一个中心 Orchestrator（编排者）持有全局任务视图：拆解子任务、派给 Worker（工作者）、收集结果、决定下一步。优点：一是全局可见，所有任务状态、预算、token 消耗集中可控；二是权限集中，可在中心统一做权限校验和速率限制；三是易于观测，整条调用链以中心为根，trace 清晰。缺点：中心是瓶颈和单点故障，编排者上下文窗口决定它能"管住"的子任务规模上限。

Swarm 没有中心节点，当前 Agent 通过 handoff（交接：任务在 Agent 间转移控制权）把任务直接转交给下一个专家，由当前节点做局部决策。优点：灵活，任务流可动态演化，适合无法预先枚举路径的开放场景；无单一瓶颈。缺点：共享上下文容易膨胀（每个 Agent 都要带上历史），终止条件难判定（可能无限转交），责任归属难追溯（"最终谁负责"不清晰），观测需要跨节点的分布式 trace 关联。

生产系统常采用混合模式：外层用 Orchestrator 控制大任务并设定全局预算与权限，内层小团队之间用 handoff 灵活流转，兼顾可控与灵活。

具体例子：一个客服系统，入口 Agent 作为 Orchestrator，把"退款、技术支持、账单"路由给三个专家；专家内部若发现是另一个部门的问题，直接 handoff 给对应专家，而不是回到中心重新派发，减少一次往返。

注意事项与取舍：选择标准本质是"可预测性 vs 灵活性"——流程越确定越倾向 Orchestrator，环境越开放越需要 Swarm。无论哪种都必须设计终止条件、超时与全局预算，否则中心化会死锁、去中心化会失控。
- 关键点：Orchestrator 中心化=可控可观测但易成瓶颈；Swarm 去中心化=灵活但终止与归因难；生产常用"中心控大局 + 局部 handoff"的混合。

### Q52. A2A 与 MCP 为什么互补？
【深度回答】
直接结论：MCP（Model Context Protocol，模型上下文协议：Agent 连接工具与数据源的标准协议）解决"Agent 如何用工具"，A2A（Agent-to-Agent：Agent 之间发现、委派与交换结果的协议）解决"Agent 如何与别的 Agent 协作"，两者处在不同协议层，互补而非替代。

分层展开原理/工程实践：
MCP 标准化"LLM 应用 → 工具/资源/Prompt"的连接。Agent 作为 MCP client 连接 MCP server，server 暴露 Tool（工具：可执行动作）、Resource（资源：可寻址的数据）和 Prompt（模板化的工作流入口）。它把"私有工具实现"变成"标准接口"，解决的是 Agent 与工具生态的互操作，即"内部怎么干活"。

A2A 标准化"Agent ↔ Agent"的协作，核心解决三件事：Discovery（发现：通过 Agent Card 找到合适的远程 Agent）、Delegation（委派：把任务以结构化形式交给远程 Agent 并跟踪 submitted/running/completed/failed 状态）、Result exchange（结果交换：接收执行结果，支持流式输出与 artifact 产物）。

两者互补的关键：一个远程 Agent 的内部实现对 A2A 客户端是不透明的——它内部完全可以依赖 MCP 调用几十个工具、访问私有记忆库，但对客户端只暴露任务级接口。A2A 在"Agent 之间"这一层做标准化，MCP 在"Agent 内部如何使用工具"这一层做标准化，正好是一上一下两个层面，互相补全。

具体例子：我的应用通过 A2A 发现并委派一个远程翻译 Agent 翻译文档；该翻译 Agent 内部通过 MCP 连接术语库、词典等工具完成工作，最后把译文作为任务结果经 A2A 返回。A2A 客户端既不需要知道翻译 Agent 用了哪些 MCP 工具，也不应看到它的内部记忆。

注意事项与取舍：A2A 不是 Agent Framework（框架：提供构建 Agent 组件的开发库），也不是 MCP 的替代品。实际系统中 A2A 管跨团队/跨组织协作，MCP 管每个 Agent 的工具接入；选型时先问"要打通的是另一个 Agent，还是工具和数据"。
- 关键点：MCP 是"Agent-工具"标准，A2A 是"Agent-Agent"标准；A2A 客户端不感知远程 Agent 内部的 MCP 工具；两者是上下层互补、不是替代关系。

### Q53. Agent Card/Skill Card 应包含哪些信息？
【深度回答】
直接结论：Agent Card（Agent 卡片：描述一个 Agent 能力、地址与发现信息的元数据）和 Skill Card（技能卡片：描述一个可复用 Skill 元数据与触发条件的元数据）本质都是"能力广告"，核心价值是让客户端/选择器可靠地发现、选择并正确调用，因此必须同时包含"给人看的描述"和"给机器用的契约"。

分层展开原理/工程实践：
Agent Card 应包含：1）身份与版本：name（名称）、description（描述）、version（版本号），用于发现与缓存管理；2）接入信息：service URL（服务地址）、支持的 transport（传输方式，如 HTTPS / Streamable HTTP）、authentication（认证方式，如 OAuth2 / Bearer）；3）能力声明：capabilities（能力列表）、支持的 Skills 列表、输入/输出模式；4）契约细节：真实接口必须有 schema（数据模式：输入输出必须遵守的数据格式）、错误语义（错误码与重试策略）和 version compatibility（版本兼容规则：向后兼容承诺，避免客户端因契约变化而崩溃）。

Skill Card 应包含：稳定 id、互斥且具体的 description（避免与其他 Skill 的触发描述重叠）、tags（标签）和典型 example（示例输入），帮助选择器做匹配；但 Skill 内部完整流程仍由 SKILL.md（技能手册：描述执行步骤、工具与验收标准的文件）承载，Card 只负责"可发现"。

安全要点是"Card 是广告，不等于授权"：客户端看到 Card 写"能订票"不能直接信任，还必须验证对方身份、检查自己的权限策略，并以 schema 校验返回结果，防止恶意或过期 Card 诱导误调用。

具体例子：一个订票 Agent 的 Card 只写"能订票"是不够的，还必须写清输入参数（城市、日期、人数、舱位）、输出格式（订单号、价格、座位）、错误码（无票/日期无效）和认证方式，客户端才能安全且正确地调用。

注意事项与取舍：Card 信息过少导致误调用，信息过详增加维护成本。推荐把"稳定的契约"（schema、错误语义、版本）与"易变的宣传"（描述、示例）分开版本管理；同时 Card 需防篡改（签名 / HTTPS），并在客户端侧做身份与权限复核。
- 关键点：Card=发现+契约，既要人可读描述也要机器可读 schema；契约必须含错误语义与版本兼容；Card 不等于授权，客户端必须验证身份与权限。

### Q54. 多 Agent 如何防止上下文污染？
【深度回答】
直接结论：核心原则是"最小共享 + 显式溯源 + 分层隔离"——默认按任务传递最小结构化上下文，而不是让所有 Agent 共享全部历史；每条信息都携带来源与可信级别，把污染面限制在单个 Agent 内部。

分层展开原理/工程实践：
1. 最小化共享（minimal context passing）：按任务把子 Agent 需要的字段单独组装传入，例如只传"订单号 + 金额"，而不是整段对话记录，直接减少无关信息进入推理上下文。
2. 溯源与可信级别（provenance：信息的来源与可信程度标注）：每条消息/文档标注来源、产生时间、可信级别（如"工具原始输出"vs"模型摘要"），让接收方识别哪些是证据、哪些是二手信息。
3. 隔离边界：按 tenant（租户）/ user（用户）/ thread（线程）做数据隔离，防止跨会话、跨用户历史混入。
4. 返回校验：对子 Agent 的返回做 schema（数据模式：输入输出必须遵守的数据格式）验证，拒绝结构异常或越界字段。
5. 中心化摘要：跨 Agent 传递的摘要由中心统一生成，并保留原始证据链接允许下游核对，避免摘要漂移污染决策。
6. 脱敏：敏感字段（身份证、密钥）在传递前脱敏或只传引用，需要时按权限回查原始值。

对于 Blackboard（黑板：多个 Agent 共享一块工作区做消息交换）模式：共享能提高协作效率，但必须有访问控制（每个 Agent 只能读写自己的分区）和版本冲突策略（reducer 或加锁），否则黑板会成为污染放大器。

具体例子：财务 Agent 只需收到"金额、发票号、支付状态"，不应看到用户与医疗 Agent 的完整对话；医疗 Agent 的检查结果经脱敏后只传"结论概要 + 证据链接"给汇总 Agent，既能协作又不泄露原始敏感数据。

注意事项与取舍：完全隔离会杀死协作收益，完全不隔离会污染决策。实际工程应做"上下文最小集"设计：先枚举每个 Agent 真正需要的最小字段，再逐项加回有证据支持必要的字段，并用 eval（评测）验证加回字段是否真的提升任务质量，避免过度加料。
- 关键点：最小结构化上下文传递是根本手段；每条信息带溯源和可信级别；tenant/user/thread 隔离 + schema 校验 + 脱敏；黑板模式必须配访问控制。

### Q55. 多 Agent 任务失败如何做补偿？
【深度回答】
直接结论：多 Agent 的失败补偿要分两类处理——纯计算步骤可安全重试或换 Agent；外部写操作必须采用 Saga（分布式事务的分步补偿：把一个长事务拆成带补偿动作的本地事务序列）模式，逐段记录状态并预定义补偿动作，绝不盲目重跑整条链路。

分层展开原理/工程实践：
1. 先定义任务状态机与幂等键：每个子任务有唯一 idempotency key（幂等键：用于识别"同一操作"的唯一标识），外部操作必须支持幂等重放，避免重复执行产生副作用。
2. 纯计算步骤（读、生成、转换）：失败可重试、换 Agent、降级模型，不产生副作用，风险低。
3. 外部写操作（扣款、下单、发消息）：使用 Saga——每一步执行后落盘记录"已提交"，并预先定义 compensation（补偿动作：撤销上一步副作用的逆向操作），失败时逆序执行补偿。
4. 聚合节点区分必需/可选子任务：必需子任务失败则整体失败并补偿；可选子任务失败允许 partial success（部分成功：只交付成功部分并明确标记缺失），提高整体可用性。
5. 人工兜底：达到重试阈值或补偿也失败时，交给 HITL（Human-in-the-Loop，人在回路：关键步骤暂停，等待人工确认或处理）。
6. 关键陷阱：不能因为 Worker 超时就假设它没执行。必须先查询真实外部状态（订单是否存在、消息是否发出）再做决策，否则可能重复扣款。

```
# 伪代码：Saga 分步补偿
for step in [支付, 发券, 发通知]:
    try:
        result = execute(step)            # 执行本地事务
        record_commit(step, result)       # 落盘"已提交"
    except Failure:
        for done in reversed(committed):  # 逆序补偿
            compensate(done)
        escalate_to_human()               # 兜底交人工
```

具体例子：一个"支付 + 发优惠券"流程，扣款成功但发券接口超时。正确做法是：先查券系统确认券未发放，再执行补偿（补发券）或记录人工介入；错误做法是直接重跑整条链，导致二次扣款。

注意事项与取舍：补偿设计要回答三个问题——"已执行了哪些副作用？""每个副作用怎么撤销？""补偿本身失败了怎么办？"（答案通常是交人工）。幂等键、状态落盘、真实状态查询这三件事做扎实，失败处理就成功了大半。
- 关键点：外部写操作用 Saga 逐段记录 + 补偿，而非整链重跑；幂等键与真实状态查询是防重复副作用的关键；可选子任务允许部分成功，兜底交人工。

### Q56. 如何评估多 Agent 系统是否真的更好？
【深度回答】
直接结论：判断"多 Agent 是否更好"的唯一标准，是与单 Agent 或固定 Workflow（工作流：程序员预先写死的固定执行路线）建立 baseline（基线：作为对照的基准实现）做端到端对比，看质量收益是否显著覆盖额外成本，而不是看架构是否"更先进"。

分层展开原理/工程实践：
要对比的指标分三组：
1. 质量类：end-to-end success rate（端到端成功率：任务真正完成的占比，以 outcome 为准）、per-worker success rate（每个子 Agent 单独成功率）、message quality（消息/中间产物质量）、delegation accuracy（委派准确率：把任务正确分给对应 Agent 的比例）。
2. 成本类：latency（端到端延迟）、token/总成本、coordination overhead（协调开销：调度、上下文复制、通信带来的额外 token 与时间）、无效 handoff（交接：任务在 Agent 间转移）次数。
3. 稳定性类：相同任务多次运行的方差、失败传播（一个 Worker 失败是否拖垮整体）、恢复成功率。

评估方法：控制变量（固定同一模型、同一 prompt 版本、同一 eval set 评测集），分别跑"单 Agent"和"多 Agent"；再看并行收益（对比串行多 Agent 与并行多 Agent，确认提升来自并行而非多角色）；最后看净收益——若准确率提升很小但成本翻倍，就应回退更简单架构；用 trajectory（轨迹：一次任务从开始到结束的完整调用链）做错误归因，区分"模型问题"和"架构问题"。

```
# 对比实验设计
baseline  = run(single_agent,  eval_set)
candidate = run(multi_agent,   eval_set)
compare(success_rate, latency, cost, variance)
```

具体例子：两个方案对比，单 Agent 用 5 个工具完成"查资料 + 写报告"，成功率 78%、成本 100 元；拆成 3 个 Worker 后成功率 82%、成本 320 元。提升 4% 但成本 3 倍，且轨迹分析发现失败多发生在汇总节点——这时应回退单 Agent 或优化汇总逻辑，而非保留多 Agent。

注意事项与取舍：多 Agent 的最大风险是"为了多而多"。评估必须坚持 outcome（环境里真正发生的结果，而不是模型口头说成功）导向，且要跑多次取分布而非单次结果；如果成本敏感，还应做"更强单模型"与"多 Agent 拆解"的替代方案对比，选更优者。
- 关键点：必须与单 Agent/固定 Workflow 建 baseline 对比端到端指标；看净收益（质量提升 vs 成本/延迟/协调开销）；用轨迹归因区分模型问题与架构问题。
