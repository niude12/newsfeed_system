# 《项目之外 · Agent 通用技术面试深度解析》

## 二、Graph、状态机与持久化执行（第 9-16 题）

### Q9. 你了解 Graph 吗？为什么 Agent 编排会使用图？

【深度回答】
直接结论：Graph（图执行结构：把多步流程建模为节点与有向边）就是把一个复杂任务画成一张能实际运行的流程图——node / edge（节点/边：执行单元与转移关系）描述"做什么、下一步去哪"，State（状态：执行过程中跨步骤传递的可持久化数据）保存大家共享的进度与数据。Agent 编排使用图，是因为 Agent 任务天然有分支、循环、并行、暂停恢复这些控制流，而图正是表达这类控制流的通用数学模型。

分层展开：
- 结构与逻辑解耦：每个 node 只负责"输入→输出"，路由决策集中在边上，编译后由运行时统一调度。这与写满 if-else 的线性代码相比，把"拓扑"和"逻辑"分开，单一职责更清晰。
- 可读与可复用：整条执行路径可视化，便于 review；一组节点可以打包成子图被多处复用。
- 可恢复与可控制：在 checkpoint（检查点：把执行进度落盘以便恢复）处保存 State，进程崩溃后能恢复；编译期能静态检查不可达节点、环上无出口等结构问题。
- 表达能力：有环图支持"循环改稿直到达标"这类迭代任务；DAG（Directed Acyclic Graph，有向无环图）支持无环的流水线并行。普通代码表达这类结构要么靠手写循环+状态记录，要么靠异常绕来绕去，图更直白。

例子：报销流程画成"识别票据→校验→审批→入账"，异常金额走条件边进入人工分支，人工确认后再回到入账节点。

注意事项：图不是银弹。只有两三个固定步骤时，普通代码反而更直观；图会带来序列化、运行时的额外成本，且"哪个节点先跑"需要额外心智负担。简单流程强行上图属于过度设计。

- 关键点：Graph=节点+边+共享 State，天然覆盖分支/循环/并行/恢复；价值在可读、可复用、可恢复、可控制；流程足够简单时不必强行上图。

### Q10. LangGraph 中 State、Node、Edge 分别是什么？

【深度回答】
直接结论：LangGraph（构建有状态多步 Agent 的图编排库）用三个概念建模：State 是跨节点流动的结构化数据，Node 是读 State 并返回增量的执行函数，Edge 决定下一个节点，其中 conditional edge（条件边：根据状态动态选择下一节点）负责路由。

分层展开：
- State：可序列化结构，如 messages、plan、retrieved_docs、error、budget。关键设计是"字段级增量更新 + reducer（归约器：合并并发写入更新的函数）"：node 只返回改动字段而非覆盖整个 State，并行分支互不踩踏。
- Node：普通函数，签名 `(state) -> partial_state`，内部调模型、调工具；不持有全局状态，易单测。
- Edge：分两类。普通 edge 无条件连 A→B；conditional edge 读取 State 结构化字段，由规则（如金额阈值）或 LLM（Large Language Model，大语言模型：能理解自然语言并生成文本的深度学习模型）决定返回下一节点名。

```python
def check_order(state): return {"amount": query_db(state["order_id"])}
def route(state): return "auto" if state["amount"] < 10000 else "review"
builder.add_conditional_edges("check_order", route, {"auto": "ok", "review": "human"})
```

例子：State 保存 `{order_id, amount}`；"查单"node 读 order_id，条件边按金额路由到自动批准或人工复核。

注意事项：State 应存原始结构化数据而非拼成文本；LLM 参与的 conditional edge 要确定性兜底，防止路由错乱。

- 关键点：State=跨节点共享的可持久化结构（增量更新+reducer）；Node=读 State 返回增量的纯函数；Edge=普通边+按状态动态路由的条件边。

### Q11. Graph 与普通 Workflow/状态机有什么区别？

【深度回答】
直接结论：它们并非对立关系——Graph 是表达 Workflow 与状态机的一种更通用形式；区别在于 Agent Graph 常把 LLM 决策作为条件边，并提供 checkpoint、streaming、interrupt 和长期运行能力。

分层展开：
- 传统 state machine（状态机：由有限状态与转移条件组成的执行模型）的"状态与转移"完全确定：给定输入，走哪条边、落到哪个状态是写死的，适合协议解析、订单流转等确定性场景。
- 普通 Workflow（工作流：按预定步骤顺序执行的流程）通常是 DAG，步骤固定、可预测，适合批处理流水线。
- Agent Graph 的三个差异：
  1. 概率性决策：条件边可以由 LLM 在"继续搜索"和"开始回答"之间选择，路径不唯一、不可穷举。
  2. 长任务能力：在每个 node 边界落 checkpoint，支持崩溃恢复、streaming（流式输出：边生成边把结果推给调用方）、interrupt（中断：在节点间暂停等待人工或外部输入）。
  3. 动态性：执行路径依赖运行时状态，而非静态定义。
- 但关键边界仍应由确定性代码约束：LLM 只负责"选策略"，权限校验、参数校验、副作用执行必须走确定性代码，否则一次模型误判可能触发危险操作。

例子：普通状态机里"支付成功→发货"的边写死；Agent Graph 可让模型根据搜索结果决定"再搜一轮"还是"开始回答"。

注意事项：确定性越强的场景，状态机越有优势——可穷举、可测试、可证明终止；Agent Graph 灵活但有不可预测性和成本，需要 guardrail（护栏：约束模型行为的多层校验与兜底）与观测。

- 关键点：Graph 是超集，Workflow/状态机是确定性子集；Agent Graph 引入 LLM 决策边+checkpoint+interrupt；危险边界仍要确定性代码兜底。

### Q12. 什么是 durable execution？

【深度回答】
直接结论：durable execution（持久化执行：进程崩溃后可从上次检查点继续）指长任务在每个可靠边界保存状态，进程崩溃、网络中断或人工暂停后能从最近成功节点恢复，而不是从头重跑。

分层展开：它比"把聊天记录存数据库"更严格，因为要保证执行语义一致。四个必要条件：
1. checkpoint（检查点：把执行进度落盘以便恢复）：在每个 node 边界序列化 State 并写入持久化存储。
2. 稳定 thread/task ID（任务标识：一次执行的全局唯一 ID）：恢复时用它定位对应检查点，而不是当成新任务。
3. 可序列化状态：State 必须能序列化，函数句柄、打开的文件、数据库连接不能进 State。
4. 幂等副作用：恢复必然涉及重放（replay：从检查点重新执行已保存的步骤），所以副作用（side effect：执行对外部环境的可观察变化，如发邮件、扣款）必须带幂等键，否则恢复时会重复扣款、重复发信。恢复前必须先判断"哪些步骤已提交、哪些可安全重放"。

```text
第1步 → checkpoint(1) → 第2步 → checkpoint(2) → ... → 崩溃
重启 → 读取 checkpoint(2) → 校验第2步的副作用是否已提交 → 从第3步继续
```

例子：任务跑到第 6 步进程崩溃，重启后从第 5 步的 checkpoint 恢复，而不是重新付费跑前 5 步。

注意事项：短任务引入 checkpoint 会带来序列化与写放大开销，并不划算；分布式环境下还要防止"两个 Worker 同时接管同一任务"，需要租约/心跳机制。

- 关键点：持久化的是"执行进度+副作用是否已提交"，而非仅聊天记录；四要素=checkpoint、稳定 task ID、可序列化 State、幂等副作用；恢复前要区分已提交与可重放。

### Q13. 为什么 Human-in-the-Loop 通常依赖 checkpoint？

【深度回答】
直接结论：因为人工审批可能几分钟甚至几天后才发生，系统必须先把图状态、待执行动作和上下文保存下来并释放进程资源，用户 approve/edit/reject 后再从同一节点恢复——这正是 checkpoint（检查点：把执行进度落盘以便恢复）要解决的问题。

分层展开：human-in-the-loop（人在回路：关键步骤需人工确认）的完整流程：
1. Agent 执行到需要审批的节点（如退款、删库、发消息），触发 interrupt（中断：在节点间暂停等待人工或外部输入）。
2. 运行时把当前 State、待执行动作、审批上下文（材料、金额、原因）序列化落盘，释放内存与进程。
3. 用户稍后通过 UI 做 approve/edit/reject（批准/修改/拒绝），结果写回 State。
4. 系统读取 checkpoint，调用 resume（恢复：从保存的检查点继续执行），从同一节点继续后续逻辑。

为什么必须持久化而不是占着内存等？因为审批可能跨分钟到跨天，长期驻留内存既贵又不抗进程重启；不保存现场，重启就丢失上下文，只能让用户重新发起。

关键工程点：在 interrupt 之前如果已发生写操作（如创建工单），该写操作必须幂等（幂等：重复执行副作用与执行一次等价）。否则恢复时会重复副作用——同一张退款单被提交两次。

```text
退款前 → interrupt(等待经理) → 落盘 checkpoint + 释放资源
经理第二天批准 → 读 checkpoint → resume 原节点 → 继续入账
```

例子：退款操作前暂停等待经理审批；第二天批准后从原节点继续，因此必须保存当时状态。

注意事项：checkpoint 应选在"副作用已完成且可验证"的可靠边界，而不是副作用执行中途，否则恢复会处于不一致状态。

- 关键点：HITL 等待时长不可控，checkpoint 是冻结现场+释放资源+恢复执行的基础；interrupt 前的写操作必须幂等；检查点选在副作用完成后的可靠边界。

### Q14. Graph 中如何实现 fan-out、join 和条件分支？

【深度回答】
直接结论：fan-out（扇出：从一个节点把独立子任务分发到多个并行节点）负责拆分发并行，join（汇合：等待多个父节点完成并聚合结果）负责收口，条件分支读取结构化 State 选择下一条边。

分层展开：
- 条件分支：conditional edge 读取 State 中的结构化字段（如 `risk_level`）返回下一节点名，可以是规则（`if amount > 10000: human_review else auto_approve`），也可以是 LLM 决策。
- fan-out：把任务列表分发到多个并行 worker。实现常见两种：显式并行边，或"一个节点写入任务列表、多个 worker 读各自切片"。前提是子任务之间无数据依赖。
- join：等全部（all）或任意（any）父节点完成再聚合。多个并发分支可能同时写同一字段，必须用 reducer（归约器：合并并发写入更新的函数）定义合并方式（append、sum、取最小等），否则后写覆盖先写。

```python
def reducer(a: list, b: list): return a + b   # 合并各分支结果
class State(TypedDict):
    results: Annotated[list, reducer]
builder.add_edge("dispatch", "worker")    # fan-out 并行
builder.add_edge("worker", "aggregate")   # join 聚合
```

例子：同时让三个 Worker 查三家供应商价格，join 等全部结果后选最低价。

注意事项：并行只适合无依赖任务；有数据依赖或共享写冲突时仍应串行或加事务（transaction：一组不可分割的操作）。join 的 all 模式可能被慢节点拖住，可配超时或 any 策略。

- 关键点：fan-out 拆无依赖任务并行；join 用 reducer 合并并发写入（all/any 可选）；条件分支读 State 动态路由；有依赖/写冲突要串行或加事务。

### Q15. Graph 中有循环时如何保证可终止？

【深度回答】
直接结论：循环边必须配显式终止条件，循环计数和最近错误要进入持久化 State（状态：执行过程中跨步骤传递的可持久化数据），编译期检查环上有出口，运行时再设全局上限兜底——四层保证图一定终止。

分层展开：
1. 显式退出条件：每个循环边带条件——质量达标、max_iterations（最大迭代次数）、deadline（截止时间）、预算（budget：成本/时间预算上限）、无进展检测、人工中止，条件不满足才继续循环。
2. 状态外置：循环计数、最近错误、已尝试方案要写进持久化 State，而不是局部变量。否则进程崩溃恢复后计数归零，可能陷入无限循环。
3. 编译期检查：静态检查"环上是否存在至少一个条件边"，完全没有出口的环直接拒绝编译。
4. 运行时全局上限：即使条件边由 LLM 判断，也要设 step/token/time 全局上限，防止模型反复误判"再试一次"。

```python
while state["iter"] < MAX_ITER and not state["quality_ok"]:
    state = improve_draft(state)      # 循环体
    state["iter"] += 1                # 计数进入 State
if not state["quality_ok"]:
    state["route"] = "escalate_to_human"   # 超限转人工
```

例子：自我改稿最多循环 3 次；第三次仍不达标就交给人工，而不是无限优化。

注意事项：单纯计数上限挡不住"每次都在做无用功但计数未超"的无效循环，所以还要加无进展检测（连续多轮输出相同、指标无改善）；终止时要保证 State 完整、可交付，而不是停在半成品。

- 关键点：循环=条件+计数，且计数必须持久化；编译期检测环上有无出口；运行时全局上限兜底 LLM 误判；无进展检测补计数上限的盲区。

### Q16. 什么时候选 LangGraph，什么时候自己写编排？

【深度回答】
直接结论：选 LangGraph（构建有状态多步 Agent 的图编排库）的时机是"状态复杂、需要暂停恢复、控制流多变"；只有几个固定步骤、同步执行且容易测试时，自定义 Python 编排更透明。

分层展开：
- 选 LangGraph 的信号：需要持久化 State 与 checkpoint、人工 interrupt、崩溃恢复、时间旅行回放；控制流含多分支/循环/并行 fan-out-join；需要 subgraph（子图：嵌套在父节点里的图，用于复用一组节点）；需要可视化图结构便于团队 review 与运维排查。
- 自己写编排的信号：步骤少且固定（如"采集→总结"两步）；同步线性执行，无分支循环并行；希望单测直连函数、不经过框架的序列化/恢复层；想避免框架锁定（framework lock-in：第三方框架带来的升级、API 变更与迁移成本）。

```python
# 自己写：两步线性流程，直接、可测
state = collect()
state = summarize(state)
return state
```

例子：只有"采集→总结"两步时自己写函数就够；需要暂停、恢复、并行和回放时再用 LangGraph。

注意事项：选择标准不是流行度，而是状态复杂度、故障恢复要求、团队调试能力和框架锁定成本。成熟做法常是混合——核心业务流程用自定义编排，只在需要恢复的局部环节接入持久化引擎，避免全盘框架化。

- 关键点：选框架看状态复杂度与故障恢复需求，不看名气；简单线性流程自研更透明易测；可局部引入持久化引擎，不必全盘框架化。
